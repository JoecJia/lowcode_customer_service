# 对话输入框支持图片与 PDF 粘贴/上传 — 改造方案

> **版本**：v0.1（方案稿）
> **最后更新**：2026-11-18
> **状态**：待评审
> **关联文档**：[产品需求说明](../../prd/06_图片与PDF附件输入.md)（用户侧需求与验收）、[开发文档](../../dev_docs/05_图片与PDF附件输入.md)（接口与实现）
> **参考样式**：用户提供的上传后输入框截图（蓝框圆角卡片、顶部图片文件卡片、底部回形针与"已上传 2 个文件"、右下蓝色主按钮）；**按钮文案固定为"发送"**，不随图片数量变化。

---

## 一、目标与范围

### 1.1 目标

1. 对话输入框支持三种附件进入方式：**Ctrl/Cmd+V 粘贴截图**、**点击回形针选择文件**、**拖拽文件到输入框**；首版为图片，PDF 可行性验证结论见「十三」。
2. 输入框视觉对齐参考图：文件卡片、文件名截断、格式与大小、底部状态栏、蓝色主按钮。
3. 附件作为 **多模态消息** 进入 Agent：图片用 `image_url` part，PDF 用 `file` part，不再被当作纯文本字符串丢弃。
4. 保留现有纯文本对话、SSE 流式、思考过程、技能调用、会话历史等全部行为。
5. 附件发送后**直接走现有对话链路**，不新增独立的"识别图片/解析文档"按钮、阶段、技能或 SSE 事件。

### 1.2 本期不做

- 不做对象存储（TOS/S3/OSS）与 CDN 签发；首版 Base64 入站、后端落盘，见「六、关键决策」。
- 不做视频/音频输入；首版仅 `image/png`、`image/jpeg`、`image/webp`（按已核对的官方示例白名单），`image/gif`、`image/bmp` 实测后再放开。
- 不做图片 OCR 或本地 PDF 文本抽取预处理；由视觉模型在普通对话中直接理解。
- 不提供"开始识别"模式：按钮始终为"发送"，有图与无图行为一致。
- 不改动知识库检索侧的图片输出逻辑（`ChatView.vue` 现有检索图片预览保持原样）。

## 三、所用模型的图片格式支持确认（已核对官方文档）

### 3.1 结论摘要

| 项 | 当前模型 `doubao-seed-2-0-pro-260215` | 推荐迁移模型 `doubao-seed-2-1-lite-260915` |
|---|---|---|
| 视觉能力 | 官方标注「多模态模型 / 深度思考 / 视觉理解」 | 官方标注「多模态理解 / 视觉理解 / 深度思考」 |
| Chat API | 支持 | 支持 |
| 图片输入格式 | `messages[].content[]` 中的 `image_url` part | 同左，链路完全一致 |
| 输入模态 | 文本、图片、视频 | 文本、图片、视频（官方视觉理解推荐模型） |
| 输出模态 | 文本 | 文本 |
| 上下文窗口 | 以模型详情页为准 | 1024K（最大输入 1024K，默认回答 4K） |
| 生命周期 | **2026-11-24 14:00（UTC+8）正式下线（EOS）** | 官方建议迁移目标 |

> 当前日期为 2026-11-18，现有模型距 EOS 仅 6 天。**不建议把新功能长期绑定在 `doubao-seed-2-0-pro-260215` 上**。图片格式两家一致，因此本期直接按官方建议迁移到 `doubao-seed-2-1-lite-260915`，代码只改配置不改链路。

官方依据：

- 火山方舟《图片理解》：<https://ark.volcengine.com/region:cn-beijing/docs/image-understanding.md>
- 火山方舟《模型列表》：<https://ark.volcengine.com/docs/model-list.md>
- 火山方舟《模型下线公告》：<https://ark.volcengine.com/region:cn-beijing/docs/model-deprecation-notice.md>
- 模型下线公告中 `doubao-seed-2-0-pro-260215` 的建议迁移模型为 `doubao-seed-2-1-lite-260915`；EOM 为 2026-09-24 10:00，EOS 为 2026-11-24 14:00。

### 3.2 确认后的请求格式（当前模型与迁移模型通用）

`image_url` 支持三种传法，本期采用第 3 种（Base64 data URL）：

```jsonc
// 1) 公网图片 URL
{ "type": "image_url", "image_url": { "url": "https://example.com/a.png" } }

// 2) Files API 上传后的 file_id
{ "type": "image_url", "image_url": { "file_id": "file-xxx" } }

// 3) Base64 data URL（本期采用）
{ "type": "image_url", "image_url": { "url": "data:image/png;base64,{base64_image}" } }
```

`detail` 可放在 `image_url` 对象内：

```json
{
  "type": "image_url",
  "image_url": {
    "url": "data:image/png;base64,{base64_image}",
    "detail": "high"
  }
}
```

完整的 user message 形态（**多图在前、文字在后**，官方对多图+单段文字的建议）：

```json
{
  "role": "user",
  "content": [
    { "type": "image_url", "image_url": { "url": "data:image/png;base64,{img1}", "detail": "high" } },
    { "type": "image_url", "image_url": { "url": "data:image/jpeg;base64,{img2}", "detail": "high" } },
    { "type": "text", "text": "这两张截图里的报错怎么解决？" }
  ]
}
```

### 3.3 按模型确认后的具体约束

| 约束项 | 确认值 |
|---|---|
| Base64 data URL 格式 | `data:{mime_type};base64,{base64_data}`，**MIME 必须小写** |
| 本期首版 MIME 白名单 | `image/png`、`image/jpeg`、`image/webp`（官方文档明确示例；`image/gif`、`image/bmp` 虽在 MIME 表中，但需实测后再放开） |
| URL 方式单图大小 | 不超过 10 MB |
| Base64 方式单图大小 | 不超过 10 MB |
| Base64 请求体 | 不超过 64 MB |
| 像素下限 | 宽 > 14 px 且高 > 14 px |
| 像素范围 | 宽×高 ∈ [196, 36,000,000] |
| 宽高比 | [1/150, 150] |
| `detail` 取值 | `low` / `high` / `xhigh`；2.0 及以后模型默认 `high` |
| `high` 模式 token | 单图固定 1280 tokens |
| `low` 模式 | token [1, 1280]，像素区间 [1764, 2257920]，速度更快 |
| `xhigh` 模式 | token [1280, 5120]，像素区间 [2257920, 9031680]，细节更强 |
| `image_pixel_limit` | 与 `detail` 同时存在时优先级更高；本期不使用 |
| 多轮会话 | Chat API 无状态，每轮请求都需重新传入图片信息 |
| 思考能力 | 迁移模型官方标注支持「深度思考」，Chat API 可用 `thinking.type` 控制；本期保留现有 `thinking.type = enabled` |

补充：官方 token 估算公式为 `min(image_width * image_height / 1764, max_image_tokens)`；`high` 固定 1280 tokens 即上限截断后的结果。

### 3.4 对方案的影响

1. 把发给模型的 `messages[].content` 从字符串升级为多模态数组；
2. 默认模型切到 `doubao-seed-2-1-lite-260915`，`text` 与 `vision` 可分别配置；
3. 在系统提示词中补充图片理解约束；
4. 前端 MIME 白名单收缩为 PNG/JPEG/WEBP；GIF/BMP 后续实测再放开；
5. `detail` 首版固定 `high`，与官方默认值一致，避免行为漂移；后续可按 `low/xhigh` 做成本与精度 A/B。

## 五、前端改造方案

### 5.1 组件拆分

建议把 `ChatView.vue:1167-1199` 的内联输入区抽成独立组件，避免主文件继续膨胀：

```text
frontend/src/components/ChatInput.vue   （新建）
```

职责：

- 维护 `inputText` 与 `pendingImages`；
- 处理 paste / drop / file input / 删除附件；
- 暴露 `send` 事件，参数为 `{ text, images }`；
- 通过 `disabled` prop 接收 `isStreaming`。

`ChatView.vue` 只保留 `@send="handleSend"` 与流式状态传递。

### 5.2 前端数据结构

```ts
interface PendingImage {
  id: string            // crypto.randomUUID()
  name: string
  mime: string          // image/png 等
  size: number          // 字节
  previewUrl: string    // URL.createObjectURL(file)
  dataUrl: string       // data:image/png;base64,...
  status: 'ready' | 'error'
  error?: string
}
```

`send` 载荷：

```ts
{
  text: string,
  images: Array<{
    name: string
    mime: string
    size: number
    data_url: string
  }>
}
```

### 5.3 交互规则

| 交互 | 行为 |
|---|---|
| 粘贴 | 读取 `clipboardData.items`，命中 `kind === 'file' && type.startsWith('image/')` 才 `preventDefault()`；非图片内容保持默认文本粘贴 |
| 点击回形针 | 触发隐藏 `<input type="file" accept="image/*" multiple>` |
| 拖拽 | 输入框显示蓝色虚线高亮；`drop` 时只接收 image 类型 |
| 删除附件 | 点击卡片右上角 `×`，同时 `URL.revokeObjectURL(previewUrl)` |
| 发送条件 | `text.trim()` 非空 **或** `images.length > 0` |
| 发送后 | 清空文本与附件列表，释放所有 objectURL；直接调用现有 `streamChat()`，无额外识别步骤 |
| 流式生成中 | textarea 禁用、附件卡片不可删、按钮变为停止方块 |
| 按钮文案 | **始终为"发送"**，不因是否上传图片而切换；流式时按现有逻辑变为停止方块 |

### 5.4 前端限制

- 单图 ≤ 10 MB；
- 图片总数 ≤ 6；
- 图片总大小 ≤ 20 MB（Base64 膨胀约 33%，仍低于 Ark 64 MB 请求体上限）；
- 不支持的格式给出行内错误提示，不弹全局 MessageBox，避免打断输入；
- 超限文件以错误态卡片展示，允许用户手动删除，不阻塞其它图片。

### 5.5 样式对齐参考图

- 外框：`border: 1px solid var(--color-primary)`、`border-radius: 12px`、白色背景；
- 聚焦：外发光 `box-shadow: 0 0 0 3px rgba(43,103,255,.10)`；
- 附件卡片：浅灰背景 `#F4F6FA`、圆角 `10px`、左侧青绿色图片图标、文件名单行省略、第二行 `PNG · 727.35KB`；
- 文本区：placeholder 改为"请将文本粘贴到此处..."，剩余高度自适应；
- 底部左：回形针图标 + `已上传 N 个文件` / `支持粘贴、拖拽或点击上传图片`；
- 底部右：沿用现有蓝色主按钮与纸飞机 SVG，**文案固定为"发送"**；流式生成中仍按现有样式切换为停止方块。

## 六、关键决策：图片如何送到后端

| 方案 | 做法 | 优点 | 缺点 | 结论 |
|---|---|---|---|---|
| A. Base64 直传 | 前端转 data URL 放进 `/api/chat` JSON | 无新接口、无存储、改动最小；Ark 官方支持 | 请求体大；历史轮次重复传；刷新后图片丢失（除非另存） | 仅作为传输方式 |
| A'. Base64 入站 + 后端落盘 | 前端仍传 Base64，后端解码后写本地文件，DB 只存元数据与文件引用 | 前端改动小；历史可回显；不撑爆 SQLite | 需文件管理与权限校验 | **首版采用** |
| B. 后端上传+本地文件 | `POST /api/uploads/image` 落 `backend/data/uploads`，返回 `image_id`；聊天只传 id | 请求体小；历史可复用 | 需清理策略、权限校验、路径安全 | 第二阶段 |
| C. TOS/Files API | 用 Ark Files API 的 `file_id` 或公网 URL | 最稳定、token 成本可控 | 引入云存储依赖与密钥配置 | 后续规模化再上 |

**决策：图片需要随对话入库。** 首版采用 A'：前端 Base64 入站，后端解码后把二进制写到本地文件，`messages.attachments` 只保存元数据和 `storage_ref`。这样既满足会话历史回显/重新生成/排障，又避免 Base64 原文进入 SQLite 导致库文件膨胀。未来切 TOS/Files API 时，只替换 `storage_ref` 的解析方式，不改消息结构。

## 七、后端改造方案

### 7.1 请求 DTO

`backend/routers/chat.py:29-32`：

```python
class ChatImage(BaseModel):
    name: str
    mime: str
    size: int
    data_url: str

class ChatRequest(BaseModel):
    session_id: str
    message: str = ""
    new_session: bool = False
    images: list[ChatImage] = Field(default_factory=list)
```

放宽"message 必填"：纯图片提问允许 `message == ""`，后端**不补任何默认识别指令**，也不触发识别技能；图片作为普通用户消息的一部分直接进入现有 Agent 对话。`backend/routers/chat.py:57` 的 `if not request.message.strip()` 改为 `if not request.message.strip() and not request.images`。

### 7.2 校验顺序

1. `len(images) <= 6`，`sum(size) <= 20MB`；
2. `data_url` 必须匹配 `^data:image/(png|jpeg|webp);base64,`；GIF/BMP 实测通过前一律拒绝；
3. 解码后实际字节数与 `size` 偏差不超过 1 KB；
4. 读取文件头魔数二次校验，禁止"改扩展名"绕过；
5. 像素限制暂由模型侧兜底；前端可在上传前用 `Image()` 读取自然宽高做提前拦截。

校验失败返回 `422`，错误信息用中文，前端展示在对应附件卡片上。

### 7.3 消息组装

新增纯函数（建议放 `backend/services/message_content.py`，便于单测）：

```python
def build_user_content(text: str, images: list[ChatImage]) -> str | list[dict]:
    if not images:
        return text
    parts = [
        {
            "type": "image_url",
            "image_url": {"url": img.data_url, "detail": "high"},
        }
        for img in images
    ]
    if text:
        parts.append({"type": "text", "text": text})
    return parts
```

要点：

- **图片在前、文字在后**，与官方多图示例一致；`text` 为空时不追加 text part，不注入任何识别提示词；
- 无图片时继续返回字符串，保证所有旧逻辑与旧会话零改动；
- system 消息仍保持字符串，`get_system_messages()` 不需要改；
- 不新增识别技能、识别阶段或 SSE 事件，发送后完全复用现有 `agent_loop_stream()`；
- 技能回注的 `<task_result>` 仍是字符串，不携带图片。

### 7.4 上下文截断兼容

`backend/services/agent_service.py:88-100` 的 `truncate_messages()` 必须同时支持两种 content：

```python
def content_weight(content) -> int:
    if isinstance(content, str):
        return len(content)
    return sum(
        len(p.get("text", "")) for p in content if p.get("type") == "text"
    ) + 1280 * sum(1 for p in content if p.get("type") == "image_url")
```

补充规则：

- 当前轮 user 消息（含图片）永远不参与丢弃；
- 历史中的图片消息按 1280 tokens 估算，超出时整轮（user+assistant）一起丢弃；
- 若历史图片过多，可降级为文本占位 `[用户上传过 N 张图片]`，但当前轮图片保留原样。

### 7.5 图片入库与历史回显

**结论：图片需要记录进对话。** 但入库分为两层：

1. `messages` 表只增列存 **附件元数据**，不存 Base64 原文；
2. 图片二进制写到本地文件，数据库只保存可解析的 `storage_ref`。

理由：

- 会话历史需要回显用户当时发了什么图；
- 重新生成、继续追问、反馈与排障都需要回溯图片；
- Chat API 无状态，续问时必须从附件存储中重新取出图片并重新注入 `image_url`；
- Base64 原文直接入 SQLite 会让数据库快速膨胀，并拖慢会话列表/历史加载。

#### 7.5.1 数据结构

`messages.content` 继续只存纯文本，保证会话列表摘要、现有前端渲染、`<task_result>` 过滤逻辑全部不受影响。

新增 `messages.attachments TEXT DEFAULT '[]'`，存 JSON：

```json
[
  {
    "id": "img_01",
    "name": "截图.png",
    "mime": "image/png",
    "size": 743296,
    "width": 1920,
    "height": 1080,
    "sha256": "3a7f...c91b",
    "created_at": 1763452800,
    "storage": {
      "type": "local",
      "ref": "sessions/{session_id}/messages/{message_id}/img_01.png"
    }
  }
]
```

字段说明：

- `id`：消息内唯一，用于删除与前端 key；
- `name/mime/size/width/height`：用于卡片展示与像素预检；
- `sha256`：去重、完整性校验、排障；
- `storage.type`：`local` / `tos` / `ark_file` / `ephemeral`；
- `storage.ref`：本地相对路径、对象存储 key 或方舟 `file_id`。

未来切 TOS/Files API 时只改 `storage.type/ref` 的解析逻辑，不改表结构。

#### 7.5.2 落盘路径

```text
backend/data/uploads/
└── sessions/
    └── {session_id}/
        └── messages/
            └── {message_id}/
                └── {attachment_id}.{ext}
```

- 路径只由服务端生成，不使用用户原始文件名，避免路径穿越；
- 目录按 session/message 隔离，删除会话或消息时可整目录清理；
- 文件权限限制在后端进程内，不直接暴露静态目录。

#### 7.5.3 读取与回注

- `session_service.append_message(..., attachments=...)` 增加可选参数；
- `GET /api/sessions/{id}/messages` 返回 `attachments` 字段，前端 `ChatMessage` 增加 `attachments?: ChatAttachment[]`；
- 用户气泡中按输入区同样的卡片样式展示附件，只读、不可删；
- 点击卡片时走带鉴权的 `GET /api/attachments/{id}/content`，校验会话归属后返回图片流，而不是公开静态 URL；
- 重新生成/续问时，后端根据 `storage_ref` 读取图片并重新构造 `image_url`，因为 Chat API 每轮都要求重新传入图片信息。

#### 7.5.4 生命周期

- 发送成功：文本与附件元数据落库，图片落盘，二者在同一请求内完成；
- 发送失败：不落库、不落盘，或清理临时文件；
- 删除会话：软删除会话时标记附件待清理，硬删除时删除文件目录；
- 容量治理：按会话 TTL（当前 1800 秒）或独立保留策略清理过期文件；具体保留天数需产品确认；
- 隐私：附件属于用户会话数据，接口必须做用户/会话归属校验，禁止公开可枚举 URL。

## 十三、PDF 上传可行性验证（在图片方案基础上）

### 13.1 结论

**可行，且不需要更换 API 或模型链路。**

- 火山方舟官方文档说明：**部分模型支持处理 PDF**，原理是把 PDF **分页处理成多图**，再用视觉能力理解文本、图片和版面信息。
- 当前默认迁移模型 `doubao-seed-2-1-lite-260915` 位于官方「视觉理解能力 → 推荐模型」清单；文档理解的支持模型范围指向该清单，因此该模型具备 PDF 文档理解能力。建议上线前用一个真实 PDF 做账号级冒烟验证。
- Chat API 本身支持 PDF 输入，因此可以继续沿用现有 `/api/v3/chat/completions`、`streamChat()`、SSE 解析与 Agent 循环。
- PDF **不是纯文本默认读取**，而是走视觉文档理解；所以扫描版 PDF 的识别质量取决于清晰度，超大/加密 PDF 可能失败。

官方依据：

- 火山方舟《文档理解》：<https://ark.volcengine.com/region:cn-beijing/docs/document-understanding.md>
- 火山方舟《对话 (Chat) API》：<https://ark.volcengine.com/region:cn-beijing/docs/chat-api.md>
- 火山方舟《模型列表》：<https://ark.volcengine.com/docs/model-list.md>

### 13.2 确认后的 PDF 请求格式

Chat API 中 PDF 使用 `type: "file"`，`file` 内 `file_data` / `file_id` / `file_url` **三选一**。

首版沿用"Base64 入站"策略，采用 `file_data`：

```json
{
  "role": "user",
  "content": [
    {
      "type": "file",
      "file": {
        "file_data": "data:application/pdf;base64,{base64_image}",
        "filename": "产品说明.pdf"
      }
    },
    {
      "type": "image_url",
      "image_url": {
        "url": "data:image/png;base64,{img1}",
        "detail": "high"
      }
    },
    {
      "type": "text",
      "text": "这两份材料里提到的导出失败怎么处理？"
    }
  ]
}
```

**关键差异（以方舟实际返回错误为准）**：PDF 的 `file_data` **需要** `data:application/pdf;base64,` 前缀，与图片的 data URL 一致；`filename` 在使用 `file_data` 时必填。前端仍可按裸 Base64 入站，由后端统一补前缀后发给模型。

其它两种方式：

```jsonc
// Files API 上传后复用（第二阶段推荐）
{ "type": "file", "file": { "file_id": "file-xxx" } }

// 公网可访问 URL
{ "type": "file", "file": { "file_url": "https://example.com/demo.pdf" } }
```

### 13.3 按官方确认的 PDF 约束

| 项 | 图片 | PDF |
|---|---|---|
| content type | `image_url` | `file` |
| 数据字段 | `image_url.url = data:image/...;base64,...` | `file.file_data = data:application/pdf;base64,...` + `file.filename` |
| MIME | `image/png` / `image/jpeg` / `image/webp` | `application/pdf` |
| 单文件官方上限 | 10 MB | Base64/URL 方式 50 MB；Files API 512 MB |
| 请求体上限 | 64 MB | 64 MB |
| 本方案首版限制 | 单图 ≤ 10 MB，总数 ≤ 6 | 单 PDF ≤ 20 MB，数量 ≤ 1；附件总原始大小 ≤ 20 MB |
| 处理机制 | 直接理解图片 | 分页转成多图后理解 |
| 页数上限 | 不适用 | 官方文档未给出明确页数上限 |
| 存储有效期 | 本地文件自行管理 | Files API 默认 7 天，可设 1–30 天 |
| 模型 | 同一视觉模型 | 同一视觉模型，无独立 PDF 模型 |
| 对话流程 | 普通对话 | 普通对话，无识别/解析阶段 |

### 13.4 对现有图片方案的增量改造

| 环节 | 是否复用 | 增量改动 |
|---|---|---|
| 输入组件 | 复用 | `accept` 增加 `application/pdf,.pdf`；卡片图标区分 PDF；按钮仍固定为"发送" |
| 前端转换 | 部分复用 | 图片转 data URL；PDF 转裸 Base64 入站并保留原文件名，后端统一补 data URL 前缀 |
| 请求 DTO | 需泛化 | 把 `images` 泛化为 `attachments: [{ kind: 'image' | 'pdf', ... }]`，或新增并列的 `files` 字段 |
| 后端校验 | 复用结构 | 增加 `%PDF-` 魔数校验、`application/pdf` MIME 校验、单文件 20 MB 限制 |
| 消息组装 | 需分支 | `build_user_content()` 按 `kind` 生成 `image_url` 或 `file` part |
| 上下文截断 | 需扩展 | `content_weight()` 统计 `type=file`；PDF 暂按 `1280 × 估算页数` 或保守 2048 tokens 计权 |
| 入库 | 复用 | `attachments` 增加 `kind`；PDF 文件同样落 `backend/data/uploads`，只存元数据与 `storage_ref` |
| 历史回显 | 复用 | PDF 卡片只读展示；点击走带鉴权的内容接口 |
| Agent/提示词 | 复用 | 不新增解析技能；多模态通用规则补一句"PDF 也是普通用户附件" |
| SSE | 完全复用 | 无新增事件，仍是 `reasoning/content/task/done` |
| 模型配置 | 完全复用 | 继续 `doubao-seed-2-1-lite-260915` |

建议把 `build_user_content()` 扩展为：

```python
def build_user_content(text: str, attachments: list[ChatAttachment]) -> str | list[dict]:
    if not attachments:
        return text

    parts = []
    for att in attachments:
        if att.kind == "image":
            parts.append({
                "type": "image_url",
                "image_url": {"url": att.data_url, "detail": "high"},
            })
        elif att.kind == "pdf":
            parts.append({
                "type": "file",
                "file": {
                    "file_data": f"data:application/pdf;base64,{att.base64}",
                    "filename": att.name,
                },
            })

    if text:
        parts.append({"type": "text", "text": text})
    return parts
```

### 13.5 验证用例

| 用例 | 输入 | 通过标准 |
|---|---|---|
| P-001 | 单页文字型 PDF + 普通问题 | 模型能回答 PDF 中明确写出的事实 |
| P-002 | 扫描版 PDF（图片型页面） | 模型能读出主要文字；不清晰时按通用规则说明看不清 |
| P-003 | 10–20 页 PDF，问跨页汇总问题 | 回答覆盖多页内容，不出现明显编造 |
| P-004 | PDF + 图片 + 文字混合提问 | 三类内容都进入同一条 user message，按普通对话返回 |
| P-005 | 仅 PDF、无文字 | 能正常发送并获得回应；不注入默认解析指令 |
| P-006 | 加密 PDF / 损坏 PDF / > 20 MB | 前端或后端拦截，给出明确错误提示 |
| P-007 | 发送后刷新页面 | `attachments` 元数据存在，PDF 卡片可回显与下载预览 |
| P-008 | 重新生成 / 继续追问 | 后端能从 `storage_ref` 重新取出 PDF 并构造 `file` part |
| P-009 | 流式输出、思考过程、技能调用 | 与图片/纯文本链路一致，无新增阶段或事件 |

### 13.6 风险与限制

1. **PDF 是视觉分页理解**：小字号、复杂表格、公式、手写体可能识别不准；截图类问题仍优先用图片。
2. **页数与上下文**：官方未给明确页数上限，但多页会转成多图，token 与延迟都会上升；首版建议限制单 PDF ≤ 20 MB、数量 ≤ 1。
3. **扫描/加密文件**：加密或低质量扫描件可能解析失败；需在 UI 给出清晰错误提示。
4. **多轮重复传输**：Chat API 无状态，PDF 与图片一样每轮都要重新传；Agent 多轮循环会放大请求体。第二阶段建议上传到 Files API，改用 `file_id`。
5. **文件名安全**：`filename` 只作为模型可见元信息，落盘文件名必须由服务端生成，避免路径穿越。

### 13.7 建议

- **P0**：完成图片链路后，立即用 P-001/P-003 做 PDF 冒烟验证；若通过，把 `images` 泛化为 `attachments` 并支持 PDF。
- **P1**：接入 Files API，把 PDF 先上传为 `file_id`，减少重复 Base64 传输，并利用 1–30 天存储有效期做历史复用。
- **不新增**"解析文档"按钮、独立技能或专用 SSE 事件；PDF 与图片一样，只是普通对话中的用户附件。
