## 二、数据库设计

### 2.1 改造表：`users`（新增权限字段）

当前 `users` 表已由 `auth_service.py` 创建，本次需新增 `can_chat` 和 `can_admin` 两个字段。

```sql
-- 已有表结构，新增权限列
CREATE TABLE IF NOT EXISTS users (
    id          INTEGER PRIMARY KEY AUTOINCREMENT,
    username    TEXT    NOT NULL UNIQUE,          -- 用户名
    password    TEXT    NOT NULL,                 -- bcrypt 哈希
    role        TEXT    DEFAULT 'user',           -- 'user' | 'admin'（保留兼容）
    avatar      TEXT    DEFAULT '',               -- 头像 URL
    can_chat    INTEGER DEFAULT 1,               -- 【新增】前台使用权限
    can_admin   INTEGER DEFAULT 0,               -- 【新增】后台管理权限
    created_at  REAL    NOT NULL,
    updated_at  REAL    NOT NULL
);
```

**改造说明**：

| 变更类型 | 列名 | 类型 | 默认值 | 说明 |
|---------|------|------|--------|------|
| 新增 | `can_chat` | INTEGER | 1 | 前台使用权限：1=可登录 `/chat`，0=不可 |
| 新增 | `can_admin` | INTEGER | 0 | 后台管理权限：1=可登录 `/admin`，0=不可 |

**向后兼容策略**：`can_chat` 默认 1（现有用户维持前台权限），`can_admin` 默认 0（只有初始 admin 账号设为 1）。使用 `ALTER TABLE ADD COLUMN` 幂等执行。

**初始管理员账号**：

| 用户名 | 密码 | can_chat | can_admin | 说明 |
|--------|------|:--:|:--:|------|
| admin | Admin123456 | 1 | 1 | 初始超级管理员，首次登录后建议修改密码 |

**迁移 SQL**：

```sql
ALTER TABLE users ADD COLUMN can_chat INTEGER DEFAULT 1;
ALTER TABLE users ADD COLUMN can_admin INTEGER DEFAULT 0;
-- 更新初始管理员权限
UPDATE users SET can_admin = 1 WHERE username = 'admin';
```

### 2.4 已有表：`feedback`（无需改造）

```sql
CREATE TABLE IF NOT EXISTS feedback (
    id          INTEGER PRIMARY KEY AUTOINCREMENT,
    session_id  TEXT    NOT NULL,
    user_id     INTEGER NOT NULL,
    created_at  REAL    NOT NULL,
    status      TEXT    DEFAULT 'pending',
    FOREIGN KEY (session_id) REFERENCES sessions(id),
    FOREIGN KEY (user_id) REFERENCES users(id)
);
-- 唯一约束：同一用户对同一对话只能反馈一次
CREATE UNIQUE INDEX IF NOT EXISTS idx_feedback_user_session ON feedback(user_id, session_id);
```

**字段说明**：

| 字段 | 类型 | 必填 | 说明 |
|------|------|:--:|------|
| `id` | INTEGER | ✅ | 自增主键 |
| `session_id` | TEXT | ✅ | 关联 sessions.id |
| `user_id` | INTEGER | ✅ | 关联 users.id |
| `status` | TEXT | ✅ | `pending`（待处理）/ `resolved`（已处理） |
| `created_at` | REAL | ✅ | 反馈提交时间 |

#### 3.2.3 POST `/api/admin/feedbacks/{feedback_id}/resolve` — 处理不满意反馈

- **功能**：管理员提交改写后的 Q&A，写入 FAQ 知识库并触发增量向量化，标记反馈为已处理
- **认证**：需要 Bearer Token + can_admin = 1

**请求体 (Request Body)**：
```json
{
  "qa_pairs": [
    {
      "question": "用户原始问题文本",
      "answer": "管理员改写后的标准回答文本"
    },
    {
      "question": "第二条用户问题",
      "answer": "第二条改写回答"
    }
  ]
}
```

**校验规则**：

| 字段 | 规则 | 错误提示 |
|------|------|---------|
| `qa_pairs` | 至少 1 条 | "至少需要一条 Q&A" |
| `qa_pairs[].answer` | 每条 A 非空 | "第 N 条回答不能为空" |

**成功响应 (200 OK)**：
```json
{
  "ok": true,
  "message": "已保存 2 条 Q&A 到 FAQ 知识库，索引已更新"
}
```

**后端处理流程**：
1. 校验 `qa_pairs` 非空且每条 answer 非空
2. 遍历 `qa_pairs`，按格式逐条追加到 `agent_config/context/faq/general_faq.md`（或对应拆分文件）：
   ```markdown
   ### Q: {question}
   A: {answer}
   ```
3. 文件拆分：当 `general_faq.md` 中 Q&A 超过 100 条时，自动拆分到 `general_faq(101-200).md`、`general_faq(201-300).md` 等
4. 调用 `vectorizer.py` 的 `update_document()` 方法做增量向量化
5. 更新该 `feedback` 记录的 `status` 为 `resolved`

**文件拆分规则**：

| 文件名 | Q&A 范围 |
|--------|---------|
| `general_faq.md` | 第 1 ~ 100 条 |
| `general_faq(101-200).md` | 第 101 ~ 200 条 |
| `general_faq(201-300).md` | 第 201 ~ 300 条 |
| `general_faq(N-M).md` | 每 100 条一组 |

const BASE = '/api/admin'

function getAdminAuthHeaders(): Record<string, string> {
  const token = localStorage.getItem('admin_token')
  const headers: Record<string, string> = { 'Content-Type': 'application/json' }
  if (token) {
    headers['Authorization'] = `Bearer ${token}`
  }
  return headers
}

export async function adminAuthFetch(url: string, options: RequestInit = {}): Promise<Response> {
  const headers = getAdminAuthHeaders()
  const resp = await fetch(url, {
    ...options,
    headers: { ...headers, ...(options.headers || {}) },
  })
  if (resp.status === 401) {
    localStorage.removeItem('admin_token')
    localStorage.removeItem('admin_info')
    window.location.href = '/admin/login'
  }
  return resp
}

## 十、补充考量

### 10.1 错误处理与边界情况

| 场景 | 前端处理 | 后端处理 |
|------|---------|---------|
| 管理端 Token 过期 / 无效 | adminAuthFetch 全局拦截 401 → 清除 Token → 跳转 `/admin/login` | 返回 401 + `{"detail": "无效的认证令牌"}` |
| 非管理员访问管理后台 | 路由守卫跳转 `/admin/login`；若无 token 则渲染登录页 | 后端 `require_admin` 返回 403 `{"detail": "需要管理员权限"}` |
| 普通用户（can_admin=0）尝试登录管理后台 | 显示 "无管理权限，登录失败"，不写入 localStorage，不跳转 | 登录接口成功但前端拦截，后端不单独处理 |
| admin 账号被取消 can_admin | 前端修改权限弹窗 admin 的 can_admin 复选框 disabled | 后端 PATCH `/api/admin/accounts/{id}/permissions` 中 admin 不可取消 can_admin |
| 反馈为空 | Toast 提示 "暂无反馈" | 返回空数组 `{ data: { feedbacks: [], total: 0 } }` |
| 文件不存在（Agent 配置） | Toast 提示 "文件不存在" | 返回 404 `{"detail": "文件不存在"}` |
| 目录遍历攻击 | — | 后端校验路径前缀必须为 `agent_config/`，拒绝 `../` 路径 |
| Q&A 文件写入失败 | Toast 提示 "保存失败" | 捕获 IOError，返回 500 `{"detail": "文件写入失败"}` |
| FAQ 文件拆分 | — | 自动检测 Q&A 条数，超过 100 条时自动拆分为新文件，最后加载的为索引文件 |
| 向量化失败 | Toast 提示 "知识库更新失败，请重试" | 捕获向量化异常，标记反馈状态仍为 pending |
| 并发处理同一条反馈 | 按钮 loading 态阻止二次点击 | 数据库 UNIQUE 约束 + 幂等：已 resolved 不可重复处理 |
| 拖拽分隔条超出边界 | 前端限制最小宽度：对话区 200px，改写区 240px | — |
| 长时间未操作导致 Session 过期 | `adminAuthFetch` 全局 401 处理 | TTL 校验 |
| 非 .md 文件点击 | el-tree 节点置灰不可点击 | GET `/api/admin/agent-config/file` 拒绝非 `.md` 文件 |

### 10.2 安全性关注点

| 关注点 | 措施 |
|--------|------|
| 密码存储 | bcrypt 加盐哈希（已有） |
| Token 存储 | 管理端使用独立 `admin_token`，与前台 `auth_token` 隔离 |
| Token 有效期 | JWT 7 天（已有） |
| 权限校验 | 后端 `require_admin` 中间件校验 can_admin == 1 |
| 路径遍历 | Agent 配置文件读取：强制校验前缀 `agent_config/`，拒绝 `../` |
| XSS | Vue 模板自动转义；marked.js 渲染仅使用 `<p>/<h1>-<h6>/<code>/<pre>/<a>/<ul>/<ol>/<li>/<strong>/<em>`，屏蔽 `<script>` |
| CSRF | SPA + Bearer Token 认证模式 |
| SQL 注入 | 参数化 SQL |
| 密码不下发 | 账号管理列表 API 不返回 password 字段 |
| admin 保护 | admin 账号不可取消 can_admin 权限 |

### 10.3 性能考量

| 场景 | 措施 |
|------|------|
| Agent 文件树遍历 | 后端递归遍历 `agent_config/` 目录（文件数 < 100），一次性返回 JSON，无分页 |
| Agent 文件内容读取 | 单文件 < 1MB，直接全文返回，前端 marked.js 客户端渲染 |
| 反馈列表分页 | 后端 offset/limit 分页，每页 20 条，前端按需加载 |
| 瀑布流加载 | 反馈列表滚动到底部触发 loadMore，避免一次加载全部数据 |
| 表格分页 | Element Plus el-pagination，每页 20 条 |
| 向量化处理 | `update_document()` 增量更新，仅处理变更的 Q&A 条目，避免全量重建索引 |
| 文件拆分渲染 | marked.js 渲染依赖已有组件，无额外开销 |

### 10.6 开发规范

- **命名规范**：Vue 组件 `PascalCase`（`AdminLoginView.vue`、`AgentConfigTab.vue`），后端文件 `snake_case`（`admin.py`、`agent_config_service.py`），API 路径 `kebab-case`（`/api/admin/agent-config/tree`）
- **注释规范**：关键业务逻辑添加 JSDoc（前端）/ docstring（后端），复杂算法如文件拆分逻辑添加行内注释
- **Git 提交规范**：`feat: 新增不满意回答处理功能`、`feat: 新增管理后台账号管理`，参考 `01_迭代开发规范.md`
- **类型安全**：TypeScript 严格模式；后端 Pydantic 模型覆盖所有请求/响应
- **CSS 变量**：所有色值使用设计规范 CSS 变量，不硬编码色值
- **文件路径**：使用绝对路径（相对项目根目录）
- **Token 隔离**：管理端 API 通过 `adminAuthFetch` 读取 `admin_token`，不得混用前台的 `authFetch`/`auth_token`
