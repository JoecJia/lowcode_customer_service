**改造说明**

| 变更类型 | 列名 | 类型 | 默认值 | 说明 |
|---------|------|------|--------|------|
| 新增 | `scope` | TEXT | `'frontend'` | 区分前台/后台会话，存量数据自动落为 `frontend` |

### 2.2 新建表：`context_change_batch`（变更批次 · 原子单元）

> **批次是确认与回滚的唯一原子单元**。一次对话中智能体可生成多个文件的变更，它们归入**同一会话下的同一个待确认批次**；管理员逐条查看 diff、继续对话调整，全部无误后**一次性确认整个批次**（N 个文件原子落盘）；出问题时**按批次原子回滚**（N 个文件一起还原）。不提供逐文件确认，避免「改了一半」的中间态。

```sql
CREATE TABLE IF NOT EXISTS context_change_batch (
    id          INTEGER PRIMARY KEY AUTOINCREMENT,
    batch_no    TEXT NOT NULL UNIQUE,            -- 批次号 b_<YYYYMMDDHHMMSS>_<6位hex>
    session_id  TEXT NOT NULL,                   -- 来源后台会话（按会话组织变更记录）
    operator    TEXT NOT NULL,                   -- 操作管理员
    status      TEXT NOT NULL DEFAULT 'pending', -- pending / applied / discarded / rolled_back
    item_count  INTEGER NOT NULL DEFAULT 0,      -- 批次内文件变更数
    summary     TEXT DEFAULT '',                 -- 整批摘要
    restored_from INTEGER,                       -- rollback 专用：被回滚的批次 id
    created_at  REAL NOT NULL,
    applied_at  REAL,
    closed_at   REAL
);

CREATE INDEX IF NOT EXISTS idx_batch_session_status
    ON context_change_batch(session_id, status, id DESC);
CREATE INDEX IF NOT EXISTS idx_batch_created
    ON context_change_batch(created_at DESC);
```

### 2.3 新建表：`context_audit_log`（文件变更明细 / 修改日志）

> 每行是批次内的**一个文件变更**，通过 `batch_id` 归属批次；既是审计日志，也是按批次回滚时的内容依据（记录前后哈希与备份路径）。

```sql
CREATE TABLE IF NOT EXISTS context_audit_log (
    id          INTEGER PRIMARY KEY AUTOINCREMENT,
    batch_id    INTEGER NOT NULL,                -- 所属批次 context_change_batch.id
    item_index  INTEGER NOT NULL DEFAULT 0,      -- 批次内序号（0..item_count-1）
    operator    TEXT NOT NULL,                   -- 操作管理员用户名
    action      TEXT NOT NULL,                   -- stage / apply / discard / rollback
    source      TEXT NOT NULL DEFAULT 'agent',   -- agent / admin_edit / rollback
    target      TEXT NOT NULL,                   -- 目标文件（相对 agent_config/ 的路径）
    base_hash   TEXT,                            -- 变更前文件 sha256（新建为 NULL）
    new_hash    TEXT,                            -- 变更后文件 sha256
    backup_path TEXT DEFAULT '',                 -- 变更前备份相对路径（供回滚）
    created_at  REAL NOT NULL
);

CREATE INDEX IF NOT EXISTS idx_context_audit_batch
    ON context_audit_log(batch_id, item_index);
CREATE INDEX IF NOT EXISTS idx_context_audit_created
    ON context_audit_log(created_at DESC);
CREATE INDEX IF NOT EXISTS idx_context_audit_target
    ON context_audit_log(target, id DESC);
```

**字段说明**

| 字段 | 类型 | 必填 | 说明 |
|------|------|:--:|------|
| `id` | INTEGER | ✅ | 自增主键 |
| `batch_id` | INTEGER | ✅ | 所属批次，关联 `context_change_batch.id` |
| `item_index` | INTEGER | ✅ | 批次内序号，保证多文件写入/回滚顺序确定 |
| `operator` | TEXT | ✅ | 管理员用户名（来自 JWT payload） |
| `action` | TEXT | ✅ | `stage`（生成草稿）/ `apply`（整批并入）/ `discard`（整批取消）/ `rollback`（整批回滚） |
| `source` | TEXT | ✅ | `agent`（智能体草稿）/ `admin_edit`（管理员直编）/ `rollback`（批次回滚） |
| `target` | TEXT | ✅ | 目标文件相对路径（相对 `agent_config/`） |
| `base_hash` | TEXT | — | 变更前文件 sha256（新建为 `NULL`）；冲突检测与回滚校验依据 |
| `new_hash` | TEXT | — | 变更后文件 sha256；用于定位历史内容 |
| `backup_path` | TEXT | — | 变更前备份相对路径（`.backup/<batch_no>/<item_index>/...`） |
| `created_at` | REAL | ✅ | 操作时间 |

**批次状态机**

```
pending ──确认(applied)──▶ applied ──回滚(rollback)──▶ rolled_back
   │
   └──取消(discard)──▶ discarded
```

> 一个会话可有多个批次：通常只保留「当前待确认批次」（pending），确认后转 applied 并可回滚；再发起新修改时创建新的 pending 批次。日志只增不改，备份随日志长期保留（见 §13.4）。

#### 3.1.1 POST `/api/admin/chat` — 后台维护智能体对话

- **功能**：以后台维护智能体（profile=`admin`）进行 SSE 流式对话
- **认证**：需要 Bearer Token + `can_admin = 1`

**请求体 (Request Body)**

```json
{
  "session_id": "a1b2c3d4e5f6...",   // 必填，必须是 scope=admin 的会话
  "message": "帮我把数据导出 FAQ 补充一下"  // 必填，非空
}
```

**校验规则**

| 字段 | 规则 | 错误提示 |
|------|------|---------|
| `session_id` | 会话存在且未软删除 | `404 会话不存在` |
| `session_id` | `scope == 'admin'` | `404 会话不存在`（不泄露存在性） |
| `message` | 去空格后非空 | `400 message is required` |

**成功响应**：`200 OK`，`Content-Type: text/event-stream`

**SSE 事件类型**

| event 类型 | data 结构 | 说明 |
|-----------|----------|------|
| `reasoning` | `{"content": "..."}` | 思考过程增量；首包为 `<THINK_V2>`，结束为 `</think>` |
| `content` | `{"content": "..."}` | 可见回答增量 |
| `title` | `{"title": "..."}` | 首条用户消息触发的自动命名结果；复用前台 `title_service`，与主回复并行推送，不等 `done` |
| `task` | `{"type": "context_transformation", "status": "executed", "result": "..."}` | 技能执行结果 |
| `change` | `{"change_id","op","target","summary","diff"}` | Context 变更待确认（新增） |
| `warning` | `{"content": "..."}` | 轮次/工具上限提示 |
| `error` | `{"content": "..."}` | 错误信息 |
| `done` | `{}` | 流结束 |

> **标题生成复用前台逻辑**：后台会话的首条用户消息落库前调用 `title_service.should_generate_title()`，创建 `generate_and_store_title()` 后台任务，并用 `chat_stream_with_title()` 包装 SSE 流推送 `title` 事件。失败静默降级、手动改名优先、乐观回写等规则完全沿用 `docs/prd/05_对话名称自动生成.md`。**不新增独立的 auto-title 接口，也不改 `llm_service`。**

**SSE 流示例**

```
event: reasoning
data: {"content":"<THINK_V2>"}

event: reasoning
data: {"content":"需要先定位数据导出相关文档"}

event: reasoning
data: {"content":"</think>"}

event: content
data: {"content":"我先检索一下知识库。"}

event: task
data: {"type":"knowledge_retrieval","status":"executed","result":"..."}

event: task
data: {"type":"context_transformation","status":"executed","result":"已生成变更，待确认"}

event: change
data: {"change_id":"c_20261110_001","op":"write","target":"context/faq/data_export.md","summary":"补充 CSV 导出限制说明","diff":"--- a/...\n+++ b/..."}

event: content
data: {"content":"已生成变更草稿，请在下方卡片确认后并入知识库。"}

event: title
data: {"title":"数据导出 FAQ 补充"}

event: done
```

#### 3.2.2 POST `/api/admin/context/batches/{batch_id}/apply` — 确认批次（N 文件原子生效）

- **功能**：把 pending 批次内所有文件变更一次性写入 `agent_config/context/`、更新索引、写日志（任一失败整批补偿回滚）
- **认证**：需要 Bearer Token + `can_admin = 1`

**成功响应 (200 OK)**

```json
{
  "ok": true,
  "message": "已并入知识库并更新索引",
  "data": { "batch_no": "b_20261119153000_a1b2c3", "item_count": 2, "index_updated": true }
}
```

**失败响应**

| 状态码 | 场景 | 响应 |
|-------|------|------|
| `404` | 批次不存在 | `{"detail": "批次不存在"}` |
| `409` | 非 pending / 任一文件 base_hash 不符 | `{"detail": "批次已处理"}` / `{"detail": "目标文件已被修改：<path>，请基于最新版本重新生成该批次"}` |
| `422` | 目标路径越界 | `{"detail": "非法的目标路径"}` |
| `500` | 写入失败（已补偿回滚） | `{"detail": "批次写入失败，已回滚已写入的文件"}` |

**处理流程**（全量预检 → 备份 → 写入 → 索引 → 单事务日志，详见 §11.6）：

> **并发约束**：阶段 1–5 全程在全局 `_BATCH_LOCK` 内串行，索引自身由内层 `_INDEX_LOCK` 保护；两管理员同时确认同一文件时，后到者预检即发现 `base_hash` 不符而返回 409，不会覆盖先到者（见 §11.7）。

1. 对批次内每个 item 校验 `realpath` 白名单与 `base_hash` 冲突，**任一失败则整批拒绝、无写入**；
2. 逐文件备份变更前内容到 `.backup/<batch_no>/<item_index>/<rel>`；
3. 逐文件原子写入（`os.replace`），中途异常则按备份补偿回滚；
4. **进程内** `update_document` + `refresh_searcher` + 单飞预热（策略 C）；
   > ⚠️ **禁止**子进程调用 `update_index.py`：`refresh_searcher()` 只在子进程生效，运行中服务仍持旧索引（见 §11.6）。
5. 单 SQLite 事务内写批次状态 `applied` + N 条明细日志。

> 索引更新失败返回 `200` + `index_updated=false` + `warning`，文件已落盘，提示手动重建。

> **409 处理路径（已拍板·走路径 1）**：`base_hash` 不符即整批拒绝、草稿作废，提示管理员**基于最新版本重新生成批次**后再确认；本期**不做自动 rebase / 三方合并**（见 §11.6）。前端收到 409 将该批次标记失效并引导重新生成，不提供「重试原批次」。

### 7.1 `useMaintenanceChat.ts` 状态设计

```typescript
import { ref, computed } from 'vue'
import { streamAdminChat } from '../api/admin'

export interface ChatMessage {
  id?: number
  role: 'user' | 'assistant'
  content: string
  reasoning?: string
  tasks?: { type: string; result: string }[]
  changes?: ContextChange[]
  isStreaming?: boolean
  error?: string
  created_at?: number
}

export interface ContextChange {
  change_id: string
  op: string
  target: string
  summary: string
  diff: string
  status: 'pending' | 'applied' | 'discarded'
}

export interface ChatTab {
  id: string
  sessionId: string
  title: string
  titleStatus: 'pending' | 'ready'
  messages: ChatMessage[]
  streaming: boolean
  error?: string
}

export function useMaintenanceChat() {
  const tabs = ref<ChatTab[]>([])
  const activeTabId = ref('')
  const visible = ref(false)
  const controllers = new Map<string, AbortController>()

  const activeTab = computed(() =>
    tabs.value.find(t => t.id === activeTabId.value) ?? null,
  )

  function openTab(sessionId: string, title = '新对话', messages: ChatMessage[] = []) {
    const existed = tabs.value.find(t => t.sessionId === sessionId)
    if (existed) {
      activeTabId.value = existed.id
      return existed
    }
    const tab: ChatTab = {
      id: `tab_${Date.now()}_${Math.random().toString(36).slice(2, 8)}`,
      sessionId,
      title,
      titleStatus: title && title !== '新对话' ? 'ready' : 'pending',
      messages,
      streaming: false,
    }
    tabs.value.push(tab)
    activeTabId.value = tab.id
    return tab
  }

  function send(tab: ChatTab, text: string) {
    const controller = streamAdminChat(
      tab.sessionId,
      text,
      { /* onContent / onReasoning / onTask / onChange / onTitle / onDone / onError */ },
    )
    controllers.set(tab.id, controller)
  }

  function dispose() {
    controllers.forEach(c => c.abort())
    controllers.clear()
  }

  return { tabs, activeTabId, activeTab, visible, openTab, send, dispose }
}
```

**要点**

- `controllers` 用 `Map` 而非 `ref`：`AbortController` 不需要响应式。
- 增量写入直接操作 `tab.messages`，**不依赖组件是否挂载**，因此收起后仍可继续生成。
- `dispose()` 在 `MaintenanceAssistant` 的 `onBeforeUnmount` 调用，避免连接泄漏。

## 十一、Context 编辑工具 `context_editor` 实现思路

### 11.1 定位与边界

`context_editor` 是**后端受控工具**（不是提示词型 Skill），由后台维护智能体通过 `<task>` 调用，负责「定位 → 读取 → 生成暂存变更」，**不直接写正式文件**。

| 能力 | 是否提供 | 说明 |
|------|:--:|------|
| 列出 context 文件树 | ✅ | 供模型定位目标文件，避免它猜路径 |
| 读取文件（大纲 / 分段 / 全文） | ✅ | 受字符上限保护，防止撑爆上下文 |
| 生成变更（新建 / 修改）到暂存区 | ✅ | 返回 `change_id` + diff，等管理员确认 |
| 列出 / 查看自己的待确认变更 | ✅ | 避免重复生成同一变更 |
| 删除文件 | ❌ | 风险高，且 `update_document` 不支持删除（见 §12 P8），本期走运维 |
| 上传 docx / 改图片资源 | ❌ | 本期不做，`assets/` 由开发侧维护 |
| 修改 `context/` 以外的文件 | ❌ | 禁止改 `agent.md` / `skills/*.md`，否则等于让智能体改写自己的提示词 |

**与既有 `context_transformation` 技能的关系**：

| | `context_transformation` | `context_editor` |
|---|---|---|
| 类型 | 提示词型 Skill（读 md 注入） | 工具型 Skill（执行后端逻辑） |
| 职责 | 描述「docx → md → 图片压缩 → 更新索引」的作业流程 | 提供「读 / 写暂存 / 查」的文件原语 |
| 运行时会做什么 | 无（当前是纯文本注入，见 §12 P0） | 真实读写文件、生成 diff |

> 结论：`context_transformation` 保留为流程说明，**执行动作全部由 `context_editor` 承担**；其 md 中对「请执行 `update_index.py`」的描述在后台场景下改为「调用 `context_editor`」，由工具内部完成索引更新。

### 11.2 为什么必须是「工具」而不是提示词

现状 `dispatch_skill` 只有三条执行路径：`knowledge_retrieval` 特判、按 `SKILL_REGISTRY` 读 md 文件拼进上下文、未命中时回退 MCP 外部工具（`skill_service.py`）。**三条路径都不具备写文件能力**。模型本身没有文件系统权限，因此：

- 仅靠提示词写「请修改 `context/faq/xxx.md`」→ 模型只会**输出一段文字宣称已修改**，文件不变、索引不变；
- 这比不给能力更危险：管理员会误以为知识库已更新。

因此必须把「写文件」包装成模型可调用的原语，并在 `dispatch_skill` 中增加 **handler 型分支**。

### 11.3 工具原语与参数契约

**单入口 + `action` 区分**（减少模型对工具名的选择成本，也便于白名单管理）：

| action | 参数 | 返回（文本，回注给模型） | 副作用 |
|--------|------|------------------------|--------|
| `list` | `path`（可选，默认 `context/`） | 目录树（路径 + 大小 + 是否有变更待确认） | 无 |
| `read` | `path`（必填）、`section`（可选，标题关键字）、`offset`/`limit`（可选，行范围） | 命中段落；无 `section` 时返回「标题大纲 + 前 2000 字」 | 无 |
| `stage_write` | `path`、`mode`、`content`、`summary` | `change_id` + diff + 变更后字符数 | 写 `.staging/`，不碰正式文件 |
| `list_changes` | `path`（可选） | 待确认变更列表 | 无 |

**参数细节**：

| 参数 | 类型 | 必填 | 约束 |
|------|------|:--:|------|
| `path` | string | 按 action | 相对 `agent_config/` 的路径，形如 `context/faq/general_faq.md`；必须以 `context/` 开头、`.md` 结尾 |
| `mode` | string | `stage_write` 必填 | `append`（追加到文末）/ `insert_after`（在指定标题段后插入，需 `after_heading`）/ `replace_section`（替换指定标题段）/ `replace_file`（整篇替换，风险最高） |
| `after_heading` | string | `insert_after` 必填 | 目标标题文本（不含 `#`），用于定位插入点 |
| `content` | string | `stage_write` 必填 | Markdown 片段；`replace_file` 时为全文 |
| `summary` | string | — | ≤50 字变更摘要，用于卡片与审计 |

> `mode` 的设计动机：`replace_file` 让模型重写整篇文档，极易丢掉未提及的段落。默认应引导模型用 `append` / `insert_after`，`replace_file` 仅在新建文件时使用（新建等价于整篇替换空文件）。

**调用示例**（`parse_tasks` 已支持 JSON 对象/数组形式，无需改解析器）：

```xml
<task>{"name":"context_editor","arguments":{"action":"read","path":"context/faq/general_faq.md","section":"数据导出"}}</task>

<task>{"name":"context_editor","arguments":{"action":"stage_write","path":"context/faq/general_faq.md","mode":"insert_after","after_heading":"数据导出","content":"- CSV 单次导出上限 5 万行，超出请分批导出。","summary":"补充 CSV 导出上限说明"}}</task>
```

**返回示例**（`stage_write`，回注给模型的 `<task_result>` 原文）：

```
已生成变更：批次 b_20261110173012_a7f3c9 的第 1 项（待确认）
目标：context/faq/general_faq.md（insert_after「数据导出」）
摘要：补充 CSV 导出上限说明
变更后字符数：+42
草稿已暂存，未写入知识库。如需调整请继续说明；全部改动无误后，请在下方批次确认条点击「确认并入（N 项）」一次性确认整个批次，不要声称已生效。
```

> 最后一句是**反幻觉约束**：模型必须知道「暂存 ≠ 生效」，且确认入口在对话内的批次确认条（非配置页），否则会在回答里宣称已更新知识库或让管理员找错地方。

### 11.4 执行链改造（代码级）

**现状缺口**：`dispatch_skill` 返回 `str`，`agent_loop_stream` 只能把它塞进 `<task_result>` 并 `yield event: task`，**没有任何通道能推送 `event: change`**（§3.1.1 要求的结构）。靠解析返回值文本里的标记再发事件是脆弱的（模型可能改写措辞），应改为结构化返回。

**改造方案**：

```python
# skill_service.py
from dataclasses import dataclass, field

@dataclass
class SkillResult:
    text: str                                  # 回注给模型的文本
    events: list[dict] = field(default_factory=list)   # 需要透传给前端的 SSE 事件

# handler 型工具注册表（与提示词型 SKILL_REGISTRY 分离）
TOOL_HANDLERS = {
    "context_editor": handle_context_editor,   # async (task, profile, operator) -> SkillResult
}

async def dispatch_skill(repo_dir: str, task, profile: str = "frontend", operator: str = "") -> SkillResult:
    # 1) profile 白名单硬校验（见 §11.8）
    if task.task_type not in AGENT_PROFILES.get(profile, []):
        return SkillResult(f"该技能未对 {profile} 智能体开放")

    # 2) handler 型优先
    handler = TOOL_HANDLERS.get(task.task_type)
    if handler:
        return await handler(task, profile, operator)

    # 3) 原有：knowledge_retrieval 特判 / 提示词型读文件 / MCP 回退
    ...
    return SkillResult(text)
```

```python
# agent_service.py（agent_loop_stream 内，原 dispatch 之后）
result = await dispatch_skill(REPO_DIR, task, profile=profile, operator=operator)
for ev in result.events:
    yield f"event: {ev['name']}\ndata: {json.dumps(ev['data'], ensure_ascii=False)}\n\n"
yield f"event: task\ndata: {json.dumps({'type': task.task_type, 'status': 'executed', 'result': result.text}, ensure_ascii=False)}\n\n"
messages.append(format_task_result(task.task_type, result.text))
```

> `profile` 与 `operator` 必须从路由层一路传入 `agent_loop_stream`，这是 **签名变更**，与 `01_迭代开发规范.md` §7.5「`agent_loop_stream` 可不改签名」矛盾，以前者为准，见 §12.1 P5。
>
> ⚠️ `AGENT_PROFILES["admin"]` 必须显式登记 `context_editor`，否则工具会被自己的白名单拦截（`01_迭代开发规范.md` §7.1 现有的 admin 技能表就漏了它，见 §12.1 P15）。

### 11.5 暂存区与批次化两阶段写入

> **变更以批次（batch）为单位暂存、确认、回滚**。一次对话中模型对多个文件的修改归入同一会话下的一个 pending 批次；管理员逐条看 diff、继续对话调整；全部无误后一次性确认整批（原子落盘），或按会话一键回滚整批（原子还原）。**不提供逐文件确认**（见 §1.2 / §13）。

**目录结构**：

```
agent_config/context/
├── .staging/                              # 待确认批次（不参与索引、不入库）
│   └── b_20261110173012_a7f3c9/           # 批次目录（batch_no）
│       ├── batch.json                     # 批次元信息（session_id / operator / summary / status）
│       └── items/
│           ├── 0/                         # item_index=0
│           │   ├── meta.json              # 单文件变更元信息
│           │   ├── old.md                 # 原文件快照（新建时不存在，op=create）
│           │   └── new.md                 # 拟写入内容
│           ├── 1/                         # item_index=1（同一批次的另一个文件）
│           │   └── ...
│           └── 2/
│               └── ...
├── .backup/                               # apply / rollback 前的正式文件备份
│   └── b_20261110173012_a7f3c9/
│       ├── 0/context/faq/general_faq.md   # item_index 分目录，保留原层级，便于整批还原
│       └── 1/context/faq/export.md
└── .faiss/                                # 向量索引（已 gitignore）
```

**`batch.json` 字段**：

| 字段 | 类型 | 说明 |
|------|------|------|
| `batch_no` | string | `b_<YYYYMMDDHHMMSS>_<6位随机 hex>`，**不用顺序号**（并发下会撞，见 §12 P10） |
| `session_id` | string | 来源后台会话，变更记录按会话组织 |
| `operator` | string | 管理员用户名（来自 JWT） |
| `summary` | string | 整批摘要 |
| `status` | string | `pending` / `applied` / `discarded` / `rolled_back` |
| `item_count` | int | 批次内文件变更数 |
| `created_at` / `closed_at` | real | 时间戳 |

**item 的 `meta.json` 字段**：

| 字段 | 类型 | 说明 |
|------|------|------|
| `batch_no` | string | 所属批次（与目录名一致） |
| `item_index` | int | 批次内序号（0..item_count-1），保证写入/回滚顺序确定 |
| `op` | string | `create` / `update` |
| `target` | string | 相对 `agent_config/` 的路径，如 `context/faq/general_faq.md` |
| `mode` | string | 生成时使用的写入模式 |
| `base_hash` | string | 生成时原文件的 sha256（新建为 `null`），apply 时用于冲突检测 |
| `new_hash` | string | 暂存内容的 sha256 |
| `summary` | string | 单文件变更摘要（对话中逐条展示 diff） |
| `source` | string | `agent` / `admin_edit` |

**对话迭代规则**：同一会话的 pending 批次可持续追加/调整——模型每次 `stage_write` 时先 `list_changes(session_id)`：同 `target` 且内容变化则**覆盖该 item 的 `new.md` 并重算 `new_hash`**（`base_hash` 不变）；新增文件则追加 item 并递增 `item_count`。管理员在对话中说「第 2 条改一下」即可定位调整，无需逐条确认。

**base_hash 的作用**：批次确认时对每个 item 比对 `sha256(当前文件) != base_hash`，任一不符则**整批拒绝** `409`、**草稿作废并要求基于最新版本重新生成该批次**（不自动 rebase），避免部分文件基于旧版本覆盖他人改动；并发串行另由 `_BATCH_LOCK` 保证（§11.6/§11.7）。

### 11.6 apply：索引必须在「服务进程内」更新（关键修正）

**错误做法**（本文档 §3.2.2 原文）：`subprocess.run(["python3", "update_index.py", "update", rel])`。

原因：`update_index.py` 在**子进程**里调用 `refresh_searcher()`，改的是子进程自己的模块级单例；子进程退出后一切消失，而正在运行的 uvicorn 进程仍持有旧的 `HybridSearcher`（旧 BM25 语料 + 旧 FAISS 句柄）。表现为：文件已改、`chunk_meta.json` 已更新，但**线上检索仍命中旧内容，直到重启服务**。

**正确做法**：在同一进程内完成「写文件 → 增量向量化 → 失效检索器单例」：

```python
# context_admin_service.py
import asyncio, os, shutil, hashlib

from skills.context_transformation.vectorizer import update_document   # 需 agent_config 在 sys.path（main.py 已注入）
from skills.knowledge_retrieval.hybrid_search import refresh_searcher, prewarm

_INDEX_LOCK = asyncio.Lock()                      # 索引自身的锁：仅保护 update_document + refresh_searcher
_BATCH_LOCK = asyncio.Lock()                      # 批次全局锁：覆盖预检→备份→写入→索引→日志全过程（消除 TOCTOU 竞态）
_background_tasks: set[asyncio.Task] = set()      # 持有后台任务引用，防止被 GC 回收

async def apply_batch(batch_no: str, operator: str) -> dict:
    """批次级原子确认：N 个文件要么全部生效，要么全部回到原状。

    整批（阶段 1–5）在 _BATCH_LOCK 内串行：预检通过的瞬间到日志提交之间不会被
    其他 apply/rollback 插入，杜绝两管理员基于同一 base_hash 确认时
    「双双向过预检、先后写入、后者覆盖前者」的 TOCTOU 竞态（见 §11.7）。
    """
    async with _BATCH_LOCK:                        # ← 锁范围从预检一直覆盖到日志提交，不可缩小
        batch = _load_batch(batch_no)
        if batch["status"] != "pending":
            raise ConflictError("该批次已处理，请勿重复确认")
        items = _load_items(batch_no)              # [{item_index, meta, new_path}, ...] 按 item_index 排序

        # —— 阶段 1：全量预检（任何一项失败都不产生写入）——
        resolved = []                              # [(item, abs_target, current_hash), ...]
        for item in items:
            meta = item["meta"]
            abs_target = _resolve_target(meta["target"])             # realpath + 白名单，见 §11.8
            current_hash = _sha256_file(abs_target) if os.path.exists(abs_target) else None
            if current_hash != meta["base_hash"]:
                # 409：目标已被他人改动 → 本批次草稿作废，重新生成（不做自动 rebase，见 §11.7）
                raise ConflictError(f"目标文件已被修改：{meta['target']}，请基于最新版本重新生成该批次")
            resolved.append((item, abs_target, current_hash))

        # —— 阶段 2：全量备份（供失败补偿与后续回滚）——
        backups = []                               # [(item, backup_rel), ...]
        for item, abs_target, current_hash in resolved:
            backup_rel = ""
            if current_hash:
                rel = os.path.relpath(abs_target, CONTEXT_DIR)
                backup_rel = os.path.join(".backup", batch_no, str(item["meta"]["item_index"]), rel)
                _backup_file(abs_target, backup_rel)
            backups.append((item, backup_rel))

        # —— 阶段 3：全量写入（失败则按备份补偿回滚已写入的文件）——
        written = []
        try:
            for item, abs_target, _ in resolved:
                _atomic_write(abs_target, item["new_path"])         # copy 到 .tmp + os.replace
                written.append((item, abs_target))
        except Exception:
            _compensate(written, backups)                           # 逆向还原，保证整批原子
            raise ApplyError("批次写入失败，已回滚已写入的文件")

        # —— 阶段 4：进程内增量索引（整批一次性失效 + 单飞预热）——
        # _INDEX_LOCK 是 _BATCH_LOCK 的内层锁，仅保护索引数据结构本身；
        # 顺序固定为先 _BATCH_LOCK 再 _INDEX_LOCK，rollback 同序，避免死锁。
        async with _INDEX_LOCK:
            results = [await asyncio.to_thread(update_document, p) for _, p in written]
            refresh_searcher()                                      # 置空单例，下次检索重建
        ok = all(results)
        if ok:
            _schedule_warmup()                                      # 后台单飞，见下方 _warmup_once

        # —— 阶段 5：整批写日志 + 事务性状态切换 ——
        _commit_batch_logs(batch_no, operator, "apply", resolved, backups,
                           source=batch["source"], status="applied", applied_at=time.time())
        return {"batch_no": batch_no, "item_count": len(items), "index_updated": ok}


def _compensate(written, backups):
    """补偿回滚：把已写入的文件按备份还原（新建文件则删除），逆序执行。"""
    backup_map = {id(item): rel for item, rel in backups}
    for item, abs_target in reversed(written):
        rel = backup_map.get(id(item), "")
        if rel:
            _restore_file(abs_target, rel)                          # 从备份 copy 回
        else:
            os.remove(abs_target)                                   # 原本是新建，直接删除
```

**并发锁分层（v1.6 修复，务必遵守）**

| 锁 | 范围 | 作用 |
|------|------|------|
| `_BATCH_LOCK` | `apply_batch` / `rollback_batch` 的**阶段 1–5 全程** | 把「预检 → 备份 → 写入 → 索引 → 日志」变成一个不可插入的临界区，消除 TOCTOU 竞态 |
| `_INDEX_LOCK` | 仅阶段 4 的 `update_document` + `refresh_searcher` | 保护索引数据结构本身；是 `_BATCH_LOCK` 的**内层锁**，顺序固定为 `_BATCH_LOCK → _INDEX_LOCK`，两函数同序，避免死锁 |
| `_prewarm_lock` | `_warmup_once()` 后台预热 | 单飞，合并多次重建请求（与上面两把锁无嵌套关系） |

> **为什么必须锁到阶段 5**：旧实现只有 `_INDEX_LOCK` 覆盖阶段 4，阶段 1 预检与阶段 3 写入在锁外。两个管理员基于同一 `base_hash` 的批次几乎同时确认时，可能**双双通过阶段 1 预检**，再先后写入同一文件，后者静默覆盖前者且双方都记 `applied`。把 `_BATCH_LOCK` 提到最外层后，先到者整批完成并提交日志，后到者进入时阶段 1 即发现 `base_hash` 不符并返回 409。

**409 base_hash 冲突的处理路径（已拍板：走路径 1）**

```
阶段 1 预检 base_hash 不符
    → 整批拒绝 409，无任何写入（原子预检）
    → 本批次草稿作废（不作为可重试单元保留）
    → 提示管理员「目标文件已被修改：<path>，请基于最新版本重新生成批次」
    → 管理员在对话中基于最新文件内容重新描述修改 → 生成新的 pending 批次 → 再次确认
```

> **本期不做自动 rebase**：不在 apply 时把草稿自动合并到最新版本。原因：草稿 diff 基于旧 `base_hash` 的文本位置，自动 rebase 需要三方合并，语义不可控且可能静默串改他人改动；让管理员在最新内容上重新生成并确认，才是可追溯、可预期的安全路径。批量生成时同理——对批次内**任一** item 冲突都按整批 409 作废处理。

**三种重建策略对比**：

| 策略 | 做法 | apply 耗时 | 副作用 | 结论 |
|------|------|:--:|------|:--:|
| A 同步重建 | apply 内 `await to_thread(prewarm)` | 10~15s | 返回即生效，无请求抖动；但接口慢，前端需长 loading | 🔵 备选（仅在要求强一致时启用） |
| B 纯懒重建 | 只 `refresh_searcher()` | <1s | 下一次检索（可能是前台用户）承担 11s，且无日志 | ❌ 废弃 |
| C 失效 + 后台预热 + 单飞锁 | 如上代码 + `_warmup_once()` | <1s | 极短窗口内并发检索会等待重建 | ✅ **已确认采用** |

> **决策（2026-11-10）**：采用策略 C。理由：`apply` 是管理员交互，必须快速反馈；而重建是幂等且可合并的后台动作，用单飞锁保证「同一时刻最多构建一次」，避免多管理员连续 apply 触发多次 11s 重建把 CPU 打满。

**单飞预热实现**（C 策略的必要组件，缺了它并发 apply 会重复构建）：

```python
# context_admin_service.py
import asyncio, sys, time

_prewarm_lock = asyncio.Lock()

def _schedule_warmup() -> None:
    """调度单飞预热，并持有任务引用防止被 GC 回收。"""
    task = asyncio.create_task(_warmup_once())
    _background_tasks.add(task)
    task.add_done_callback(_background_tasks.discard)

async def _warmup_once() -> None:
    """单飞预热：同一时刻最多一个重建任务；已在构建则直接返回。"""
    if _prewarm_lock.locked():          # 事件循环单线程，判断与加锁之间无 await，无竞态
        return
    async with _prewarm_lock:
        t0 = time.perf_counter()
        try:
            ready = await asyncio.to_thread(prewarm)
            print(
                f"[context] 索引重建完成 ready={ready} 耗时 {(time.perf_counter() - t0) * 1000:.0f}ms",
                file=sys.stderr, flush=True,
            )
        except Exception as exc:        # 预热失败不影响已落盘的文件
            print(f"[context] 索引预热失败：{exc}", file=sys.stderr, flush=True)
```

**重建窗口内前台检索的真实行为**（必须在验收时知道，否则会误判为 bug）：

- 检索链路 `_get_searcher()` 是**同步阻塞**构建：窗口内的第一个检索请求会等待约 11s；
- 但它读的是**最新的** `chunk_meta.json`，因此**结果一定是新内容，只是慢**；
- 不会出现「命中旧内容」——旧内容只在 `refresh_searcher()` 之前才可能返回。

**前端表现约定**（C 策略下的交互契约）：

| 时机 | 表现 |
|------|------|
| `apply_batch` 返回 `200` + `index_updated=true` | 批次置「已并入」，该会话的变更记录条目显示「已生效」，确认按钮消失、出现「一键回滚」 |
| 同上，附带弱提示 | 变更记录条目灰色小字「索引更新中，约 10 秒内生效」，**不阻塞**输入与其他操作 |
| `index_updated=false` | 条目标黄 + 「已写入，但索引更新失败，请手动重建」 |
| 重建期间用户提问 | 正常对话；若恰好命中首个检索，等待时间会偏长（约 11s），无需前端特殊处理 |

**`update_document` 的语义边界**：

- 支持：文件已存在（替换旧 chunks）、文件新增（追加 chunks）。
- **不支持：文件删除**（`os.path.exists` 为 False 直接返回 False，旧 chunks 残留）。本期不开放删除，规避该缺陷。

### 11.7 并发与幂等

| 场景 | 措施 |
|------|------|
| 多个批次 apply / rollback 同时触发 | 全局 `_BATCH_LOCK` 串行化「预检→备份→写入→索引→日志」**全过程**；索引自身再由内层 `_INDEX_LOCK` 保护；重建由 `_warmup_once()` 的 `_prewarm_lock` 单飞 |
| **两个管理员基于同一 `base_hash` 同时确认同一文件** | `_BATCH_LOCK` 保证串行：先到者整批生效并更新文件哈希；后到者进入后阶段 1 预检即发现 `base_hash` 不符 → 整批 `409`，**草稿作废、需基于最新版本重新生成**，不会覆盖前者（TOCTOU 已消除） |
| 批次内某文件已被他人改动 | 阶段 1 全量预检 `base_hash`，任一不符 → 整批 `409`，**无任何写入**，草稿作废并提示重新生成（原子预检；不自动 rebase） |
| 写入中途异常 | `_compensate()` 按备份逆向还原已写入文件（新建则删除），整批回到原状（原子补偿） |
| 重复点击「确认变更」 | `batch.status != pending` → `409 批次已处理`；接口幂等返回上次结果 |
| 同一会话内模型重复 stage | `list_changes(session_id)` 让模型先查 pending 批次；同 `target` 覆盖 item 的 `new.md`，不堆叠批次 |
| 同一会话已有 pending 批次又发起新修改 | 复用该 pending 批次追加/调整 item；仅当上一批已 applied 才创建新批次 |
| 暂存区堆积 | 启动时 + 每小时清理 `created_at` 超过 `CONTEXT_STAGING_TTL_SECONDS` 且 `status=pending` 的批次目录 |
| 批次日志与状态不一致 | `_commit_batch_logs()` 在**单个 SQLite 事务**内写批次状态 + N 条明细日志，要么全写要么全不写 |

```python
AGENT_CONFIG_DIR = os.path.realpath(os.path.join(PROJECT_ROOT, "agent_config"))
CONTEXT_DIR = os.path.join(AGENT_CONFIG_DIR, "context")

def _resolve_target(rel_path: str) -> str:

```

### 11.9 索引扫描必须排除暂存区与备份区

`iter_md_files()`（`agent_config/skills/context_transformation/vectorizer.py`）当前只跳过 `.faiss`：

```python
# 现状：丢弃了 dirnames，无法剪枝，.staging / .backup 会被遍历并索引
for dirpath, _, filenames in os.walk(root):
    if ".faiss" in dirpath:
        continue
```

**后果**：全量 rebuild 时，未确认的暂存内容（`.staging/*/new.md`）与历史备份（`.backup/*/xxx.md`）都会被写入索引 → 检索命中「还没确认的草稿」和「已被回滚的旧版本」，同一问题出现新旧两个答案。

**修正**：

```python
_SKIP_DIRS = {".faiss", ".staging", ".backup"}

for dirpath, dirnames, filenames in os.walk(root):
    dirnames[:] = [d for d in dirnames if d not in _SKIP_DIRS]   # 剪枝，连遍历都不进入
    ...
```

> 注意：本文档 §6.4 把该改造写在 `search_service.py`，实际位置是 `vectorizer.iter_md_files()`，`search_service` 只是薄封装。见 §12 P2。

### 11.10 错误码与降级

| 场景 | HTTP / 工具返回 | 前端表现 |
|------|----------------|---------|
| 路径越界 / 非 `.md` | 工具返回错误文本（模型可见）；API `422` | 卡片不生成 |
| 目标文件不存在且 `op=update` | 工具提示「文件不存在，若为新建请用 `append`/`replace_file`」 | — |
| 同类变更已存在 | 返回已有 `change_id`（幂等） | 复用原卡片 |
| apply 时文件被他人改过（`base_hash` 不符） | `409 目标文件已被修改，请基于最新版本重新生成` | 卡片标红、**批次作废**，引导基于最新版本重新生成（不自动 rebase） |
| apply 时暂存已过期 | `404 变更不存在或已过期` | 卡片置灰 |
| 索引更新失败（`update_document` 返回 False） | `200` + `index_updated=false` + `warning` | 提示「已写入，但索引更新失败，请手动重建」 |
| 索引重建中再次 apply / rollback | 排队等待 `_BATCH_LOCK`（外层串行），再取内层 `_INDEX_LOCK` | 按钮 loading |
| 工具调用超上限 | `close_out` 收尾（现有逻辑保留） | 正常输出兜底话术 |

> `index_updated=false` 时**必须明确告知管理员「文件已改、检索未生效」**，并在审计中记 `warning`。此时进程内 BM25 仍读旧 `chunk_meta.json`，重启后才一致。

### 11.11 与前端 `event: change` 的对接

```json
{
  "change_id": "c_20261110173012_a7f3c9",
  "op": "update",
  "target": "context/faq/general_faq.md",
  "summary": "补充 CSV 导出上限说明",
  "diff": "--- a/context/faq/general_faq.md\n+++ b/context/faq/general_faq.md\n@@ -12,3 +12,4 @@\n ## 数据导出\n - 支持 CSV / Excel\n+- CSV 单次导出上限 5 万行，超出请分批导出。"
}
```

- `diff` 由后端用 `difflib.unified_diff` 生成（上限 4000 字符，超出截断并附 `diff_truncated: true`）；
- 前端 `ContextChangeCard` 直接渲染 `event: change` 携带的 diff（批次内每个 item 一条；量大时列表流只带摘要，卡片按需补拉明细）；
- `event: change` 携带 `batch_no` / `item_index`，同一批次的卡片归组，末尾插入 `ContextBatchConfirmBar`；
- 批次状态机：`pending → applied | discarded`（回滚在配置页弹窗执行），与 `context_change_batch.status` 对应；
- 确认是批次级：`ContextBatchConfirmBar` 调 `POST .../batches/{batch_id}/apply` 一次确认整批，N 张卡片状态同步更新。

## 十三、修改日志与批次回滚

> 本章回答两个问题：① 每次变更如何留痕；② 出问题后如何**按会话对多个文件原子回滚**。
>
> 结论先行：**确认与回滚都以「批次」为唯一原子单元**。批次来自一个后台会话下的一次/多轮对话，包含 N 个文件变更；确认时 N 个文件一起生效，回滚时 N 个文件一起还原，绝不出现「改一半 / 回滚一半」。逐文件确认已取消（见 §1.2）。

### 13.1 设计目标与原则

| 目标 | 说明 |
|------|------|
| 批次可追溯 | 每个批次写一条 `context_change_batch`（会话 / 来源 / 状态 / 摘要），批次内每个文件写一条 `context_audit_log`（前后哈希 / 备份路径） |
| 按会话组织 | 变更记录按 `session_id` 归档；配置页「变更记录」弹窗按会话展示**已生效**批次（可一键回滚），pending 批次不显示 |
| 入口分离 | 确认/取消在对话内批次确认条执行；回滚在配置页弹窗执行；两者职责单一 |
| 原子确认 | 批次内 N 文件全量预检通过才写入；写入异常按备份补偿回滚（§11.6），数据库状态与日志在单事务内提交 |
| 原子回滚 | 按批次一键回滚 N 文件；全量校验通过才还原，任一失败整批不动 |
| 回滚即新批次 | `rollback` 生成一个**新批次**（status=`rolled_back`、`restored_from` 指向原批次），不删除历史，可再次回滚；日志只增不改 |
| 索引与文件一致 | 确认与回滚都走 §11.6 的进程内索引更新，杜绝「文件回退、检索仍命中新内容」 |
| 安全边界不变 | 回滚同样受 `realpath` 白名单、仅 `context/**/*.md`、`can_admin` 约束 |

### 13.2 批次与回滚链模型

```
会话 S1：
  批次#1  apply   b_...01  2 文件 [faq/a.md, faq/b.md]  → applied
  批次#2  apply   b_...02  1 文件 [faq/c.md]           → applied
  批次#3  rollback b_...03  2 文件（还原批次#1）        → rolled_back, restored_from=1
         └─ 把 a.md/b.md 恢复为批次#1 apply 前的状态；不删除 #1/#2，新增 #3
```

**关键约束**：

- `batch.id` 全局单调递增，作为批次号；按 `session_id` 查询即为该会话的变更记录；
- 回滚内容来自批次确认时写入的备份 `.backup/<batch_no>/<item_index>/<rel>`（「变更前」快照），N 个文件按 `item_index` 顺序还原；
- 回滚前全量校验 `sha256(当前文件) == 批次各 item 的 new_hash`，任一不符 → `409`，整批不动；
- 回滚后写新批次记录 + N 条明细日志（`source=rollback`），`restored_from` 指向被回滚批次，形成可追溯链。

### 13.3 回滚可行性分析

| 维度 | 现状 | 结论 |
|------|------|------|
| 原始内容是否留存 | 批次 apply 前逐文件备份到 `.backup/<batch_no>/<item_index>/` | ✅ 具备，保留目录层级（§11.5/§11.6） |
| 批次归属 | `batch.json` + `context_change_batch` 记录 session_id、状态、item_count | ✅ 已建模（§2.2/§11.5） |
| 内容定位 | 凭 `backup_path` 取回内容、`new_hash` 校验 | ✅ 具备 |
| 原子性 | 全量预检 + 补偿回滚 + 单事务日志 | ✅ 已设计（§11.6） |
| 查询接口 | 无 `GET .../batches` | ❌ 需新增（§13.5.1） |
| 确认/回滚接口 | 无批次级 apply / rollback | ❌ 需新增（§13.5.2/§13.5.3） |
| 回滚后索引 | 若只 cp 回文件不更新索引，将命中旧内容（P1 重现） | ❌ 必须复用 §11.6 进程内更新 |

**总判断**：底层数据（备份 + 哈希 + 批次归属）已足以支撑原子回滚，缺的是批次级接口与索引联动。补齐后即为完整的「按会话多文件一键确认 / 一键回滚」。

### 13.4 备份与保留策略

| 项目 | 策略 |
|------|------|
| 备份内容 | 批次确认前，把批次内**每个变更文件的变更前内容**按 `<batch_no>/<item_index>/<原目录层级>` 复制到 `.backup/` |
| 与日志绑定 | 备份相对路径写入 `context_audit_log.backup_path`，`batch_id` + `item_index` 唯一定位 |
| 保留期 | `.backup` **不做 TTL 自动清理**，长期保留；回滚历史上限 = 保留的全部批次 |
| 容量上限（可选） | 保留最近 `CONTEXT_VERSION_KEEP`（默认 50）个批次；超出清理最旧备份及其日志，但**被 `restored_from` 引用的批次不得删除** |
| gitignore | `.staging/`、`.backup/` 均加入 `.gitignore`（运行期数据不入版本库） |
| 索引排除 | `vectorizer.iter_md_files()` 剪枝 `.staging` / `.backup` / `.faiss`（§11.9），写入/回滚前同样校验 |

> 区分两套历史：**git 历史**记录开发期人工提交；**批次备份 + 审计日志**记录运行期在线变更与回滚。二者独立、互为补充。

#### 13.5.2 POST `/api/admin/context/batches/{batch_id}/apply` — 确认批次（N 文件原子生效）

- **功能**：把 pending 批次内所有文件的变更一次性落盘并更新索引（调用 `apply_batch`，§11.6）

- **认证**：需要 Bearer Token + `can_admin = 1`

**处理流程**

> **并发约束**：步骤 1–5 全程与 `apply_batch` 共用同一把全局 `_BATCH_LOCK`，保证「回滚 vs 确认」「回滚 vs 回滚」串行，杜绝 TOCTOU 竞态；锁顺序固定为 `_BATCH_LOCK → _INDEX_LOCK`（第 4 步内层），与 §11.6 一致，避免死锁。

1. 读取 `batch_id` 对应批次及其 items；要求 `status ∈ {applied, rolled_back}`（pending/discarded 不可回滚）。
2. **全量预检**：对每个 item 用 `backup_path` 取回变更前内容，校验 `sha256(备份内容)` 与 item 的 `base_hash` 一致（新建文件 `base_hash=null`，备份不存在，回滚时删除该文件）；校验当前文件 `sha256 == new_hash`，任一不符 → `409`，整批不动。
3. **全量还原**：按 `item_index` 顺序，从备份 copy 回（新建文件则删除），任一失败按当前快照补偿回滚（与 §11.6 `_compensate` 对称）。
4. **进程内索引**：全部还原后在 `_BATCH_LOCK` 的内层 `_INDEX_LOCK` 内逐个 `update_document` + `refresh_searcher` + 单飞预热（同 §11.6）。
5. **写新批次**：`status=rolled_back`、`source=rollback`、`restored_from=batch_id`、N 条明细日志（`source=rollback`），单事务提交。

**失败响应**

| 状态码 | 场景 | 响应 |
|-------|------|------|
| `404` | 批次不存在 / 备份内容缺失 | `{"detail": "批次不存在或备份内容已不可恢复"}` |
| `409` | 任一文件当前内容与 new_hash 不符 | `{"detail": "文件已被修改：<path>，请刷新后重试"}` |
| `422` | 目标路径越界 | `{"detail": "非法的目标路径"}` |
| `500` | 备份校验失败 / 还原失败（已补偿） | `{"detail": "回滚失败，已还原到回滚前状态"}` |

---

> 原「按单文件恢复任意版本」的接口（`versions/{id}/restore`）不采用：多文件改动需要多文件原子回滚，按批次回滚才能避免中间态。若将来需要「回退到某文件更早版本」，可基于批次备份扩展，本期不做。

### 13.6 写入引擎复用关系

确认与回滚共用 §11.6 的原子写入与索引更新机制，避免行为漂移：

| 操作 | 核心函数 | 原子保障 | 索引更新 |
|------|---------|---------|---------|
| 批次确认 | `apply_batch()`（§11.6） | 预检 + 补偿 + 单事务日志 | 进程内 `update_document` + `refresh_searcher` + 单飞预热 |
| 批次回滚 | `rollback_batch()`（§13.5.3） | 预检 + 补偿 + 单事务日志 | 同上 |
| 管理员直编 | 生成本地 pending 批次（单 item）→ 走 `apply_batch()` | 同上 | 同上 |

> 直编不再绕过批次：管理员直接编辑文件后，先生成单 item 的 pending 批次再确认，从而与智能体草稿共用同一套原子确认/回滚与审计（日志 `source` 区分 `agent` / `admin_edit`）。

#### 13.7.5 Composable 状态

**（A）对话内确认 `useBatchConfirm.ts`（新建）**

```typescript
import { ref } from 'vue'
import { applyContextBatch, discardContextBatch } from '../api/admin'

export function useBatchConfirm() {
  const confirmVisible = ref(false)
  const submitting = ref(false)
  const activeBatchNo = ref('')

  function confirm(batchNo: string) { activeBatchNo.value = batchNo; confirmVisible.value = true }

  async function submit(action: 'apply' | 'discard'): Promise<{ ok: boolean; status?: number }> {
    submitting.value = true
    try {
      const resp = action === 'apply'
        ? await applyContextBatch(Number(activeBatchNo.value))   // 实际用 batch.id
        : await discardContextBatch(Number(activeBatchNo.value))
      if (resp.ok) confirmVisible.value = false
      return { ok: resp.ok, status: resp.status }
    } finally { submitting.value = false }
  }

  return { confirmVisible, submitting, confirm, submit }
}
```

**（B）配置页历史 `useBatchHistory.ts`（新建）**

```typescript
import { ref, computed } from 'vue'
import { getContextBatches, rollbackContextBatch, type ContextBatch } from '../api/admin'

export function useBatchHistory() {
  const visible = ref(false)
  const confirmVisible = ref(false)
  const loading = ref(false)
  const rollingBack = ref(false)
  const batches = ref<ContextBatch[]>([])
  const activeBatch = ref<ContextBatch | null>(null)

  const groupedBySession = computed(() => {
    const map = new Map<string, ContextBatch[]>()
    for (const b of batches.value) {
      const key = b.session_id || '其他'
      if (!map.has(key)) map.set(key, [])
      map.get(key)!.push(b)
    }
    return [...map.entries()].map(([session_id, list]) => ({ session_id, title: list[0]?.session_title || '', batches: list }))
  })

  async function open() {
    visible.value = true
    await load()
  }
  async function load() {
    loading.value = true
    try {
      const resp = await getContextBatches('applied,rolled_back')   // 仅已生效
      batches.value = ((await resp.json()).data?.batches) ?? []
    } finally { loading.value = false }
  }
  function confirmRollback(b: ContextBatch) { activeBatch.value = b; confirmVisible.value = true }
  async function rollback(): Promise<{ ok: boolean; status?: number }> {
    if (!activeBatch.value) return { ok: false }
    rollingBack.value = true
    try {
      const resp = await rollbackContextBatch(activeBatch.value.id)
      if (resp.ok) { confirmVisible.value = false; await load() }
      return { ok: resp.ok, status: resp.status }
    } finally { rollingBack.value = false }
  }
  return { visible, confirmVisible, loading, rollingBack, batches, groupedBySession,
           activeBatch, open, load, confirmRollback, rollback }
}
```

**要点**

- 两个 composable 职责单一：对话内只 apply/discard，配置页只查询已生效 + rollback；
- 配置页查询**后端按 status 过滤**（`applied,rolled_back`），pending 不下发，前端也不展示确认按钮；
- 错误码由返回值交给组件映射文案，composable 不耦合 UI。

#### 13.7.6 校验与错误提示

| 场景 | 前端处理 | 说明 |
|------|---------|------|
| 配置页弹窗 | 只显示已生效，无「确认并入」按钮 | pending 由对话内确认条处理 |
| applied 批次 | 显示「一键回滚」 | 整批回滚；不提供单文件回滚 |
| rolled_back 批次 | 显示「已回滚 → #id」 | 不可再回滚（如需再回滚基于新状态） |
| 确认/回滚期间 | `submitting` / `rollingBack` 期间按钮 loading 禁用 | 防重复提交 |
| 无记录 / 加载中 | 空状态「暂无已生效的变更记录」/ 骨架屏 | — |
| 后端 401 | `adminAuthFetch` 统一跳登录 | 无需组件处理 |
