# 07 — 双智能体拆分需求说明

> 智能客服系统 — 将单一客服智能体拆分为「前台客服智能体」与「后台维护智能体」，并赋予后台维护智能体安全的知识库编辑能力
>
> 关联文档：`docs/dev_docs/04_双智能体拆分.md`、`docs/01_迭代开发规范.md` §7（T-007）、`docs/prd/02_客服对话页.md`、`docs/prd/03_管理员后台页.md`、`docs/prd/05_对话名称自动生成.md`

---

## 一、背景与现状

### 1.1 现状描述

当前系统只有**一个**客服智能体：管理员与普通用户在前端共用同一套提示词（`agent_config/agent.md`）、同一套技能白名单和同一个对话入口。后台管理页（`AdminView.vue`）仅提供三个静态 Tab（Agent 配置查看、不满意回答、账号管理），管理员无法与智能体对话，更无法自助维护知识库。

| 位置 | 现状 |
|------|------|
| `agent_config/agent.md` | 唯一系统提示词，包含面向终端用户的功能咨询话术 |
| `backend/services/skill_service.py:47` | `get_system_messages()` 无参数，全站统一渲染 |
| `backend/routers/chat.py` | 唯一对话入口 `POST /api/chat`，`get_current_user`（`can_chat`）鉴权 |
| `backend/database.py:51` | `sessions` 表无 `scope` 字段，前台会话单池 |
| `backend/routers/admin.py` | 只有账号管理、Agent 配置查看接口，无对话 / Context 编辑接口 |
| `agent_config/context/` | 知识库文件由开发侧手工维护 + 跑脚本更新索引，管理员无自助入口 |

**问题**：

1. 管理员想补充一条 FAQ、修正一处过时说明，必须找开发人员改文件、重建索引，链路长、响应慢；
2. 单一智能体无法兼顾「对用户的客服话术」与「对维护者的文件操作能力」两类截然不同的职责，若把写文件能力开放给前台，任何用户都能构造指令改写知识库与系统提示词；
3. 知识库变更没有审批与留痕，出问题无法追溯和回滚。

### 1.2 本次变更要解决的问题

1. 把智能体按**职责**拆成前台客服、后台维护两个角色，二者**共用一套运行引擎**，仅在提示词、技能白名单、入口鉴权上区分；
2. 为后台维护智能体提供**安全的知识库编辑能力**：可定位、读取、生成变更，但任何写入都需管理员在界面上「二次确认」后才真正生效；
3. 前后台会话、技能、Token **相互隔离**，杜绝越权；
4. 全部知识库写操作**可追溯、可回滚**。

## 二、目标与非目标

### 2.1 目标

| 编号 | 目标 |
|------|------|
| G1 | 前台客服智能体行为**完全不变**，普通用户无感知 |
| G2 | 管理员可在后台以对话方式让维护智能体定位、读取、修改知识库文档 |
| G3 | 两类智能体的技能权限**硬隔离**：前台绝无写文件能力，后台仅开放维护类技能 |
| G4 | 两类会话按 `scope` 隔离，互不混池、互不越权读写 |
| G5 | 知识库写入采用「对话生成草稿 → 对话内确认 → 落盘」两阶段；以**会话批次**为原子单元，N 个文件同时生效；回滚在配置页按会话一键执行，未确认不生效 |
| G6 | 知识库写入前自动备份，写入后增量更新检索索引，无需重启即可检索到新内容 |
| G7 | 所有写操作记录审计日志（操作者 / 时间 / 动作 / 文件 / 摘要） |
| G8 | 后台维护助手以悬浮对话框形态存在于管理后台，支持多对话 Tab 与历史记录 |

### 2.2 非目标（本次不做）

| 编号 | 非目标 | 说明 |
|------|--------|------|
| N1 | 物理拆分 `agent_config/` 目录为 frontend / admin 两套 | 采用「提示词 + 白名单」逻辑分流，避免改资源路径与索引扫描，降低改动面 |
| N2 | 给后台智能体开放任意 Shell / 任意脚本执行 | 仅允许受控工具与白名单脚本，禁止命令拼接 |
| N3 | 通过对话删除知识库文件 | `update_document` 不支持删除且旧索引 chunk 会残留；删除走运维，本期不开放 |
| N4 | 通过对话上传 docx / 修改图片资源 | `assets/` 由开发侧维护，本期工具仅支持 `.md` 文本 |
| N5 | 让后台智能体修改 `agent.md` / `skills/*.md` 等系统提示词 | 写范围硬限制在 `context/` 目录下 |
| N6 | 前后台会话实时互通 / 共享上下文 | 仅共享知识库文件，对话上下文严格隔离 |
| N7 | 多管理员之间会话按人隔离 | 后台会话全局共享，`user_id` 仅记录创建者 |
| N8 | 后台对话的无障碍 / 国际化适配 | 沿用现有后台语言与交互规范 |

## 三、用户与角色

| 角色 | 鉴权 | 入口 | 可用智能体 | 知识库权限 |
|------|------|------|-----------|-----------|
| 普通用户 | `auth_token`，`can_chat=1` | 前台 `/chat` | 前台客服智能体 | 只读检索 |
| 管理员 | `admin_token`，`can_admin=1` | 后台 `/admin` 悬浮维护助手 | 后台维护智能体 | 受控写入（两阶段确认） |

**权限铁律**：后台 Token 不能读写前台会话，前台 Token 不能调用任何后台接口；技能白名单在**执行入口**硬校验，而非仅靠提示词约束。

## 四、核心概念

| 概念 | 说明 |
|------|------|
| Profile（智能体画像） | `frontend` / `admin`，决定系统提示词与技能白名单，复用同一套 `agent_loop_stream` 引擎 |
| Scope（会话归属） | `frontend` / `admin`，`sessions` 表新增字段，会话列表与读写按 scope 过滤 |
| 技能白名单 | `AGENT_PROFILES`：前台=业务咨询类技能，后台=`context_transformation` / `temporary_context_management` / `knowledge_retrieval`（只读） |
| `context_editor` | 后端**受控工具**，后台智能体通过 `<task>` 调用，提供 `list` / `read` / `stage_write` / `list_changes` 四种原语，只写暂存区 |
| 批次（batch） | **原子变更单元**。一次会话对话中模型对多个文件的修改归入同一 pending 批次；确认时 N 文件一起生效，回滚时 N 文件一起还原，无「改一半」中间态 |
| 两阶段写入 | 阶段一：对话生成草稿到 `.staging/<batch_no>/`，逐条展示 diff、对话内调整；阶段二：在对话内批次确认条一次性确认整个批次 |
| 悬浮维护助手 | 挂载在管理后台右下角的圆形按钮，展开为悬浮对话框，**不占侧边栏 Tab**，全部后台页面可见 |
| 变更卡片 | 对话消息中展示的单条变更 diff（目标文件、摘要、diff），**只展示不操作**；要改内容继续对话说明 |
| 批次确认条 | 对话内批次末尾的操作条，对 pending 批次执行「确认并入（N 项）/ 取消」 |
| 变更记录 | Agent 配置页顶部一个「变更记录」**按钮**，点击弹窗按会话查看**已生效**批次（`applied`/`rolled_back`）并「一键回滚」；待确认的不显示、不平铺 |

## 五、功能需求

### 5.1 前台客服智能体（保持现状）

- 沿用现有 `POST /api/chat` 与前台全部功能（咨询、检索、反问、反馈、附件）；
- 装配系统消息时显式指定 `profile=frontend`，并校验目标会话 `scope=frontend`；
- 前台**不得**获得 `context_editor` 等任何写工具；普通用户即使构造 `<task>{"name":"context_editor"}` 也应被拒绝，且无写操作发生。

### 5.2 后台维护智能体对话

- 新增 `POST /api/admin/chat`，需 `can_admin=1`，以 `profile=admin` 运行，SSE 流式返回；
- 后台智能体可用技能仅限维护类（`context_transformation` / `temporary_context_management` / `knowledge_retrieval` 只读），其中 `knowledge_retrieval` 用于改文档前定位内容；
- 后台智能体可调用 `context_editor` 工具完成「列目录 / 读文件 / 生成变更 / 查待确认变更」；
- 工具执行结果需要以结构化 `change` 事件推送前端，驱动变更卡片渲染，而**非**仅在文本中描述「已修改」。

**反幻觉要求**：工具生成暂存变更后，返回给模型的结果必须明确告知「暂存 ≠ 生效」，告知模型须在回复中提示管理员点击确认卡片，禁止声称知识库已更新。

### 5.3 悬浮维护助手入口与对话框

| 状态 | 表现 |
|------|------|
| 收起态 | 管理后台右下角圆形悬浮按钮（48×48），图标 + tooltip「维护助手」 |
| 展开态 | 悬浮对话框（约 480×680），固定右下角，距边 24px |

- 使用 `v-show` 切换，**禁止 `v-if`**：收起时对话框与 SSE 连接、Tab 状态全部保留，生成继续（为「静默生成」能力打底）；
- 对话框包含：工具栏（历史记录 / 新建对话 / 收起）、多 Tab 条、消息区、输入区；
- 输入区 Enter 发送、Shift+Enter 换行；当前 Tab 流式生成中时禁用发送；
- 后台各页面均可见该入口，不占用侧边栏 Tab。

### 5.4 多 Tab 与历史记录

- 支持同时打开多个后台会话 Tab，各自独立 `sessionId`、独立流式状态，互不影响；
- 「历史记录」弹窗按 `scope=admin` 拉取会话列表，支持按标题过滤；点击某条：
  - 已在 Tab 中 → 直接激活；
  - 未在 Tab 中 → 加载历史消息后新建 Tab；
- 提供重命名（手动 1–50 字）；本期不提供「AI 重新生成」（与 `docs/prd/05` 的 N5 一致）；
- 对话流由 composable 统一持有，与组件挂载状态解耦：切换 / 收起 / 展开均不中断，关闭页面时统一中止所有连接。

### 5.5 会话自动命名（复用前台逻辑）

- 后台会话标题生成**完全复用**前台已有的 `title_service`，不新增独立接口、不改造 `llm_service`（详见 `docs/prd/05_对话名称自动生成.md`）；
- 首条用户消息落库时自动触发后台任务，流式期间通过 SSE `title` 事件推送结果；生成期间 Tab 标题显示「新对话」，收到事件后回显 ≤20 字标题；
- 失败静默降级、手动改名优先、乐观回写等规则与前台一致；未收到 `title` 事件时保持「新对话」，不阻塞对话；
- 标题仅自动生成一次；之后仅可手动改名，无 `force` 重新生成入口。

### 5.6 知识库批次化两阶段写入

> **以会话批次为原子单元**：一次对话对多个文件的修改归入同一 pending 批次；确认时全部生效，回滚时全部还原，不出现「改一半」。

**阶段一：对话生成草稿（智能体侧）**

- 管理员在对话中提出修改诉求（如「在数据导出 FAQ 末尾补充 CSV 上限，并同步总览」）；
- 后台智能体通过 `context_editor` 完成定位、读取与多文件写入，归入**同一会话的 pending 批次** `.staging/<batch_no>/items/{0,1,...}/`；
- 对话流对每个文件推送 `change` 事件，前端渲染变更卡片（**只展示 diff，无确认按钮**），此时**正式知识库文件未发生变化**；
- 管理员若想调整某条，继续在对话中说明（如「第 2 条改成……」），模型**覆盖该 item 的草稿**，不新建批次、不堆叠。

**阶段二：对话内确认（管理员侧）**

- 该批次的变更卡片下方显示「批次确认条」，标注「本批次共 N 项变更」；
- 全部改动无误后在**对话内**点「确认并入（N 项）」（二次确认）：
  - 后端**全量预检**（所有文件路径合法 + 未被他人改动）→ 全量备份 → 全量原子写入 → 进程内增量更新索引 → 单事务写日志；
  - 任一文件预检失败则整批 `409`、无写入、**草稿作废并提示基于最新版本重新生成**（不自动 rebase）；写入中途异常则按备份补偿回滚，整批回到原状；
- 确认与回滚全程由全局 `_BATCH_LOCK` 串行（索引自身再取内层 `_INDEX_LOCK`），两管理员同时确认同一文件时先到者生效、后到者预检即 409，不会相互覆盖；
- 也可在对话内点「取消」丢弃 pending 批次；确认/取消后批次确认条转为对应状态，N 张卡片状态同步；
- 确认后立即生效，**无需重启服务**即可检索到新内容；
- pending 批次超过 TTL（默认 24h）自动清理。

### 5.6.1 修改日志与批次回滚

- **修改日志**：每个批次写一条批次记录（会话 / 来源 / 状态 / 摘要），批次内每个文件写一条明细（操作者、时间、目标文件、变更前后内容哈希与备份路径）；日志只增不改；
- **按会话组织**：变更记录按 `session_id` 分组，配置页「变更记录」弹窗按会话展示**已生效**批次；
- **一键回滚**：在配置页弹窗对已应用批次整批回滚（N 文件一起还原）；回滚作为**新批次**记录（`restored_from` 指向原批次），不删除历史、可再次回滚、全程可追溯；
- **回滚后立即生效**：与确认相同，回滚后检索即刻命中还原后的内容，无需重启；
- **安全约束**：确认/回滚需管理员权限与路径白名单校验；批次内任一文件被他人改动则整批拒绝（原子预检）、草稿作废并基于最新版本重新生成，不自动 rebase；确认/回滚由 `_BATCH_LOCK` 全程串行；备份内容哈希校验失败则终止；
- **来源区分**：日志标记来源为「智能体草稿 / 管理员直编 / 批次回滚」，便于统计与追责。
- **前端入口分离**：
  - 确认/取消：对话内批次确认条（pending 批次）；
  - 查看历史/回滚：Agent 配置页顶部「变更记录」**按钮 → 弹窗**，弹窗**仅显示已生效**（`applied`/`rolled_back`）批次，**不显示 pending、不平铺在页面上**；已应用批次提供「一键回滚」（二次确认）。

> 详细的数据模型、接口定义、回滚流程与前端组件设计见 `docs/dev_docs/04_双智能体拆分.md` §2.2、§11.6 与 §13。

### 5.7 会话隔离与数据可见性

- `sessions` 表新增 `scope` 字段（`frontend` / `admin`，默认 `frontend`），存量数据自动归为前台；
- 前台会话列表 / 消息 / 读写只认 `scope=frontend`，后台只认 `scope=admin`；
- 访问不属于本 scope 的会话一律返回「会话不存在」，**不泄露其存在性**。

## 六、交互流程

### 6.1 后台首轮对话 + 自动命名

```
前端（维护助手）                       后端（FastAPI）
────────────────                      ──────────────
1. 点击「新建对话」
2. ── POST /api/admin/sessions ─────▶ 3. create_session(scope=admin)
4. ◀── 201 { session_id } ──────────
5. 新建 Tab（标题「新对话」）
6. 输入问题并发送
7. ── POST /api/admin/chat ─────────▶ 8. require_admin + scope 校验
                                      9. 首条消息 → should_generate_title（复用）
                                     10. 创建标题后台任务（不阻塞主回复）
                                     11. 装配 profile=admin 系统消息
                                     12. agent_loop_stream（SSE）
13. ◀── reasoning / content / task / change / title / done
14. 收到 title → Tab 标题「新对话」→ 生成标题（不等 done）
15. 标题任务 → generate_and_store_title → 回写 sessions.title
16. 收到 done → 渲染完成
```

### 6.2 历史记录 → 多 Tab

```
1. 点击「历史记录」→ GET /api/admin/sessions（scope=admin）
2. 展示会话列表（标题 / 时间 / 最后一条消息摘要）
3. 点击某条：
   ├─ 已在 Tab 中 → 激活该 Tab
   └─ 未在 Tab 中 → GET /api/admin/sessions/{id}/messages → 新建 Tab 并加载
```

### 6.3 知识库批次化两阶段写入

```
管理员：「补充数据导出 FAQ，并同步总览」
   │
   ├─ 后端：模型多次调用 context_editor.stage_write
   │        → 同一会话建立 pending 批次 → .staging/<batch_no>/items/{0,1}/
   ├─ 前端：收到 change 事件 ×2 → 渲染 2 张变更卡片（仅 diff，无按钮）
   │
   ├─ 管理员「第 2 条改成……」（对话调整）
   │        → 覆盖 item#1 草稿，不新建批次
   │
   ├─ 管理员在对话内批次确认条点「确认并入（N 项）」
   │     → 全量预检（路径/冲突）→ 全量备份 → 全量原子写入
   │     → 进程内索引更新 → 单事务日志 → 批次「已生效」
   │     （全程 _BATCH_LOCK 串行；任一预检失败 → 409 整批拒绝、草稿作废需重新生成；写入异常 → 补偿回滚）
   │
   ├─ 管理员在对话内点「取消」（pending）
   │     → 删除暂存目录 → 审计
   │
   └─ 需要撤销时到配置页「变更记录」弹窗点「一键回滚」
         → 全量校验 → 按 item 原子还原 → 索引更新 → 新 rolled_back 批次
```

### 6.4 收起 / 恢复与多 Tab 并发

- Tab A 生成中点击「收起」→ 组件隐藏但连接与消息缓冲保留，A 继续生成；
- 切到 Tab B 发送新问题 → 独立连接，A / B 并行；
- 展开后恢复各 Tab 消息与 loading 状态；
- 关闭页面 → 统一 abort 所有连接。

## 七、权限与安全需求

| 关注点 | 要求 |
|--------|------|
| 权限校验 | 后台全部接口 `require_admin`（`can_admin=1`）；灰度开关关闭时后台接口同样拒绝 |
| 会话越权 | 双入口按 `scope` 校验，跨 scope 返回 404，不泄露存在性 |
| 技能越权 | `dispatch_skill` 入口按 profile **执行层硬校验**，超范围直接拒绝；白名单不是提示词渲染层面的软约束 |
| 改到系统提示词 | 写范围硬限 `context/`，`agent.md`、`skills/*.md` 只读不写 |
| 路径遍历 | `os.path.realpath` 后必须位于 `agent_config/context/` 内，拒绝 `../` 与 `.staging/.backup/.faiss` |
| 命令注入 | 禁用 `shell=True`，脚本路径硬编码、列表传参；本期不开放任意脚本执行 |
| 写入安全 | 批次化两阶段确认，未确认不落盘；仅允许 `.md` 白名单类型；确认前自动备份 |
| 原子性 | 批次内 N 文件全量预检通过才写入；写入异常按备份补偿回滚；日志单事务提交；回滚同理 |
| 并发冲突 | 批次 apply 时对每个文件基于 `base_hash` 检测冲突，任一不符则整批 `409`、无写入、**草稿作废并基于最新版本重新生成**（不自动 rebase）；apply / rollback 全程由 `_BATCH_LOCK` 串行，杜绝两管理员同时确认同一文件时相互覆盖（TOCTOU） |
| 内容注入 | diff 用纯文本逐行渲染，禁止 `v-html`；模型写入内容仅存储不渲染 |
| 审计 | 批次与文件明细均写日志，含操作者、来源、目标、会话、前后哈希、备份路径、时间 |
| Token 隔离 | 管理端 `admin_token` 与前台 `auth_token` 分离 |

## 八、异常处理矩阵

| 场景 | 前端表现 | 后端处理 |
|------|---------|---------|
| 管理员 Token 过期 / 无效 | 拦截 401 → 清 Token → 跳登录 | 返回 401 |
| 非管理员访问后台接口 | — | 返回 403 |
| 灰度开关关闭 | 隐藏悬浮入口 | 后台接口返回 403 |
| 访问跨 scope 会话 | 提示「会话不存在」并移除 Tab | 返回 404 |
| 前台用户构造 `context_editor` 指令 | 无变更卡片 | 返回「该技能未对 frontend 智能体开放」，无写操作 |
| 流式传输中断 | 保留已接收内容，提示可重试 | 发送 `error` 事件 |
| 自动命名失败 | 保留「新对话」，不阻塞 | 降级取首句前 20 字 |
| pending 批次缺失 / 超 TTL | 对话内批次确认条不再显示 | 定时清理，批次列表不返回 |
| 重复确认 / 取消 / 回滚 | 按钮按状态不渲染 | 返回 409「批次已处理」 |
| 批次内某文件已被他人改动（含并发同时确认） | 对话内提示「文件已变更、批次已作废，请基于最新版本重新生成」 | 返回 409，整批未写入（原子预检），草稿作废、不自动 rebase；`_BATCH_LOCK` 保证后到者不会覆盖先到者 |
| 确认/回滚写入中途异常 | 提示「操作失败，已还原（文件未改动）」 | 按备份补偿回滚，整批回到原状，返回 500 |
| 备份内容校验失败 | 提示「备份损坏，已终止」 | 返回 500，文件未写入 |
| 目标路径越界 | 不生成卡片 | 工具返回错误文本；接口 422 |
| 索引更新失败 | 提示「已写入，但索引更新失败，请手动重建」 | 返回 `index_updated=false` + warning |
| 索引重建窗口内检索 | 无需特殊处理，首查约 11s 但结果为新内容 | 后台单飞预热；窗口内结果一定为新内容 |
| 空历史记录 | 显示「暂无历史对话」 | 返回空数组 |

## 十、验收标准

- [ ] 普通用户的前台登录 / 对话 / 历史 / 反馈 / 账号管理全流程与改造前一致，无感知差异；
- [ ] 前台用户构造 `<task>{"name":"context_editor"}` 被拒绝，知识库文件无任何变化；
- [ ] 管理员在后台右下角可见悬浮维护助手，收起 / 展开不丢失对话与 Tab 状态；
- [ ] 「新建对话 → 提问」后，流式期间收到 `title` 事件，Tab 标题由「新对话」变为 ≤20 字中文标题（无需等待 `done`）；
- [ ] 历史记录可打开旧会话为 Tab，多 Tab 可各自独立流式生成，收起后仍继续；
- [ ] 对话要求修改多个文件时，生成多张变更卡片（仅 diff）+ 1 个批次确认条，正式 `context/` 文件内容未变；
- [ ] 对话中调整某条草稿后，同一 pending 批次对应 item 内容更新、不产生新批次；
- [ ] 对话内批次确认条显示「本批次共 2 项变更」；配置页「变更记录」弹窗**不显示 pending 批次**；
- [ ] 在对话内点击「确认并入（2 项）」：2 个文件**同时**生效、`.backup` 有备份、审计新增批次 + 2 条明细，前台**无需重启**即检索到新内容；
- [ ] 批次内某文件被他人改动后确认：收到 409 且**两个文件都未改动**（原子预检），批次作废并提示基于最新版本重新生成；写入中途异常时已写入文件被补偿回滚；
- [ ] 两管理员基于同一 `base_hash` 并发确认同一文件：先到者整批生效、后到者收到 409 且不覆盖前者，无「双双 applied」（`_BATCH_LOCK` 串行）；
- [ ] 对话内点「取消」：暂存批次清除，正式文件不变；
- [ ] 构造 `../../.env` 等恶意路径被拒绝，返回 422 / 工具错误文本；
- [ ] 全量重建索引后，检索不命中 `.staging` 草稿与 `.backup` 旧版本；
- [ ] 关闭灰度开关后，悬浮入口隐藏且后台对话接口返回 403；
- [ ] 配置页「变更记录」按钮打开弹窗，仅列出 `applied`/`rolled_back` 批次（不平铺、无 pending）；
- [ ] 弹窗内点「一键回滚」：批次内所有文件**同时**还原，前台**无需重启**即检索到还原后的内容；
- [ ] 回滚后新增一条 `rolled_back` 批次（`restored_from` 指向原批次），历史未被删除，可再次回滚；
- [ ] 回滚时某文件已被他人改动收到 409，整批未还原；备份内容校验失败收到 500 且文件未被写入。
