# 09 - 工具调用协议原生化改造需求说明

> 智能客服系统 — 将 Agent 工具调用从文本 `<task>` / `<task_result>` 协议迁移到方舟原生 Function Calling，消除跨轮工具结果污染导致的答非所问
>
> 关联文档：`docs/prd/02_客服对话页.md`、`docs/prd/03_管理员后台页.md`、`docs/prd/07_双智能体拆分.md`、`docs/dev_docs/09_工具调用协议原生化改造.md`
>
> 分工：本文定义用户可感知的问题、目标、行为规则与验收标准；模型 payload、代码级改动与状态模型见配套开发文档

---

## 一、背景与现状

### 1.1 现状描述

| 位置 | 现状 |
|------|------|
| `backend/routers/chat.py:114-123` | 历史消息按数据库 `role` 原样回传；工具结果因以 `role=user` 落库，会进入下一轮模型上下文 |
| `backend/services/skill_service.py:192-201` | 工具执行结果统一包装为 `role=user` 的 `<task_result>` 消息 |
| `backend/services/agent_service.py:731-733` | 工具结果写入数据库；助手原始 `<task>` 规划只存活于当前请求、不落库 |
| `backend/services/skill_service.py:56-58` | 工具协议要求模型收到 `<task_result>` 后“必须严格按 Skill 文件中定义的执行步骤完成任务” |
| `backend/services/skill_service.py:143-164` | 普通 Skill 回注完整 `.md` 指令文件并带强制遵循前缀；`knowledge_retrieval` 回注检索命中文本与图片 |
| `backend/services/agent_service.py:93-110` | 上下文超过 64000 字符权重时从历史头部按 2 条一组截断，system 消息始终保留 |
| `frontend/src/views/ChatView.vue:84` | 前端历史渲染时隐藏 `role=user` 且以 `<task_result>` 开头的假用户消息 |

**问题**：

1. 同一会话连续提出两个无关问题时，上一轮遗留的 `<task_result>` 以 `user` 身份要求模型“严格按某 Skill 执行”，导致第二个问题被旧 Skill 流程、旧检索结果或旧链接带偏；
2. 助手原始 `<task>` 规划不落库而 `<task_result>` 落库，跨轮后形成“有工具结果、无对应规划/提问”的无头上下文；
3. 工具结果以 `user` 角色长期占用跨轮上下文权重，挤压真实问答；
4. 角色语义错误：工具结果既不是用户输入，也不是助手输出，却伪装成 `user`；
5. 部分错误回注包含内部路径或工具名，既无用户价值也存在信息泄露风险。

### 1.2 根因 / 可用能力 / 本次变更要解决的问题

- **根因**：当前用文本 `<task>` 标签模拟工具调用，工具结果只能借 `user` 角色回注，且被持久化进跨轮历史。
- **可用能力**：火山方舟 Chat Completions API（`https://ark.cn-beijing.volces.com/api/v3/chat/completions`）支持原生 `tools` / `tool_calls`，`messages.role` 支持 `tool`，工具结果以 `{"role":"tool","tool_call_id":...}` 回注；项目当前默认模型 `doubao-seed-2-1-lite-260915` 在官方模型列表中标注支持函数调用。
- **本次要解决的问题**：在不改变前端交互与 SSE 事件契约的前提下，完成工具调用协议原生化，使工具结果只在当前请求内有效、角色语义正确、跨轮历史只保留真实问答。

## 二、目标与非目标

### 2.1 目标

| 编号 | 目标 |
|------|------|
| G1 | 同一会话中连续提出无关问题，第二次回答以当前用户最后一条消息为准，不被上一轮工具结果或 Skill 指令带偏 |
| G2 | 工具调用结果仅对当前 Agent 请求可见，不进入跨轮历史消息 |
| G3 | 工具结果使用语义正确的 `role=tool`，不再伪装为 `user` |
| G4 | 工具结果内容精简：不回注整份 Skill `.md`、不回注内部路径、不夹带面向用户的指令性文字 |
| G5 | 前端“思考过程”展示、SSE 事件契约与后台 `context_editor` 批次确认流程保持不变 |
| G6 | 64000 字符权重截断只作用于真实问答对，不再被工具结果无谓占用 |

### 2.2 非目标（本次不做）

| 编号 | 非目标 | 说明 |
|------|--------|------|
| N1 | 改变前端页面结构或交互方式 | 通过后端映射保持现有契约，前端代码无需改动 |
| N2 | 更换模型或 API 地址 | 现有模型与 v3 Chat Completions 地址已支持原生 tools |
| N3 | 重构 Skill 业务逻辑本身 | 检索算法、知识库内容、MCP 工具实现不在本次范围 |
| N4 | 在前端展示 `tool_call_id`、调用参数等原生字段 | 本期只迁移协议，不新增可视化字段 |
| N5 | 物理删除历史库中已存在的 `<task_result>` 记录 | 通过读取时过滤兼容旧数据，清理任务后续评估 |

## 三、核心概念与状态模型

### 3.1 概念定义

| 概念 | 说明 |
|------|------|
| 工具调用消息 | `role=assistant` 且包含 `tool_calls` 的消息；仅存在于当前请求 `messages` 中，不写入跨轮历史 |
| 工具结果消息 | `role=tool`，带 `tool_call_id`，与对应 `tool_calls[].id` 一一匹配；仅存在于当前请求中 |
| 跨轮历史 | 从数据库读取并回传模型的消息，只包含用户文本/附件与助手最终可见回答 |
| 思考过程步骤 | 保存在 assistant 消息 `steps` 字段中的 `reasoning` / `task` 步骤；不进入模型历史，只供前端回放 |
| 展示过滤 | 前端对旧数据中 `role=user` 且以 `<task_result>` 开头消息的隐藏逻辑，作为兼容兜底保留 |

### 3.2 规则与优先级

| 编号 | 规则 |
|------|------|
| R1 | 当前用户最后一条 `user` 消息的优先级高于历史中任何工具回执或 Skill 指令 |
| R2 | 历史消息中不得保留 `<task_result>` 内容；读取旧数据时必须过滤 |
| R3 | 工具结果只在当前 Agent 循环内有效；循环结束即丢弃，不落库 |
| R4 | 每个 `tool_call` 必须有且仅有一条对应的 `tool` 结果消息；顺序为 `assistant(tool_calls) → tool(...)` |
| R5 | 前端契约优先：后端必须将原生 `tool_calls` 映射为现有 `event: task` 和 `steps`，禁止透传新 event 给前端 |
| R6 | Skill 完整指令不再作为工具结果回注；思考过程卡片中不再出现整份 Skill 文档原文 |

## 四、功能需求 / 核心规则

### 4.1 场景总览

| 场景 | 用户可感知结果 | 系统行为 |
|------|---------------|----------|
| A 同一会话连续问无关问题 | 第二个问题得到针对当前问题的回答，不引用上一轮工具内容 | 跨轮历史不含上一轮工具结果 |
| B 触发知识检索 | 思考过程显示检索卡片与检索词，最终回答基于本次检索 | 检索结果仅当前轮有效 |
| C 触发反馈表链接生成 | 正常收到链接，历史里不残留旧链接 | 链接仅当前轮有效 |
| D 后台知识库维护 | 变更卡片正常显示、可确认；模型仍提示“草稿未生效” | `context_editor` 工具结果仅当前轮有效，`change` 事件契约不变 |
| E 调用 MCP 工具 | 思考过程显示工具执行结果 | MCP 结果映射为原生 tool 结果，图片按规则处理 |
| F 工具失败或越权 | 给出简短错误提示，不出现内部路径 | 错误以 `role=tool` 当前轮回注；详细路径写服务端日志 |
| G 刷新或翻页历史 | 不出现 `<task_result>` 假用户消息；思考过程可还原 | 旧数据读取时过滤；新数据不再落库 |

### 4.2 跨轮问答隔离

- 新请求到达时，历史 `messages` 只装载 `user` 文本/附件与 `assistant` 最终可见回答；
- 助手的 `reasoning_content` 与 `steps` 继续落库供前端展示，但不进入发往模型的 `messages`；
- 旧会话中遗留的 `<task_result>` 在读取阶段过滤，不进入模型上下文，也不在前端展示。

### 4.3 工具执行回执

- 模型需要调用工具时，后端从原生 `tool_calls` 中读取函数名与参数；
- 工具执行后，以 `role=tool` + `tool_call_id` 回注当前请求；
- 多工具并行调用时，每个 `tool_call` 都必须回注一条结果；
- 工具结果内容按类别精简：Skill 指令、检索全文、旧链接、文件内容、内部路径不再进入跨轮历史。

### 4.4 前端思考过程保持

- 后端继续发送 `event: reasoning`、`event: content`、`event: task`、`event: change`、`event: title`、`event: done`；
- `event: task` 的字段保持 `{ type, status, result, query? }`；
- assistant 消息继续保存 `steps`，供刷新后回放；
- 前端代码不作改动。

### 4.5 后台维护闭环保持

- `context_editor` 继续提供 `list` / `read` / `stage_write` / `list_changes` 四种原语；
- 草稿生成后继续通过 `event: change` 推送前端确认卡片；
- 工具协议中“暂存 ≠ 生效、须在对话内确认批次”的规则保持；
- 前台智能体仍不得调用任何后台写工具。

## 五、交互流程

### 5.1 单次请求消息流

1. 前端 POST `/api/chat` 或 `/api/admin/chat`，请求体不变；
2. 后端读取并按 R2 过滤历史，只装载真实问答；
3. 后端装配 `system` 消息与原生 `tools` 定义；
4. 模型返回 `tool_calls` 时，后端将 assistant 工具调用消息加入**当前请求** `messages`；
5. 后端执行工具，逐条回注 `role=tool` 消息，并 emit `event: task` / `event: change`；
6. 无更多工具调用后，模型给出最终内容；后端 emit `event: content` 与 `event: done`；
7. 仅用户消息与助手最终可见回答落库；工具调用消息与工具结果消息丢弃。

### 5.2 跨轮历史生命周期

1. 第 N 轮：用户消息 + 工具调用消息 + 工具结果消息 + 助手回答，共同存在于本轮 `messages`；
2. 本轮结束：只把用户消息与助手回答写入数据库；
3. 第 N+1 轮：从数据库读取历史时，只得到真实问答，不再看到上一轮工具结果；
4. 旧数据兼容：读取阶段发现 `<task_result>` 直接跳过。

## 六、异常处理矩阵

| 场景 | 前端表现 | 后端处理 |
|------|---------|---------|
| 工具执行失败 | 思考卡片显示简短错误，最终回答说明失败 | 以 `role=tool` 回注 `TOOL_ERROR: <type>: <简短原因>`，详细路径写日志 |
| 模型生成非法 JSON 参数 | 不中断会话，可提示重试或给出兜底回答 | 校验 `arguments`，轻微非法 JSON 可修复，修复失败则回注错误 |
| 多工具调用部分失败 | 成功的工具卡片正常显示，失败的显示错误 | 每个 `tool_call` 都回注对应结果，不跳过失败项 |
| 模型返回 `tool_calls` 但未执行完即超时 | 保留已输出内容，显示生成失败/可重新生成 | 走统一收尾逻辑，保证用户拿到最终回复 |
| 前台请求后台写工具 | 不产生变更卡片，提示无权限 | 白名单硬校验拒绝，`role=tool` 回注简短错误，知识库无写入 |
| 旧历史含 `<task_result>` | 该条消息不展示 | 读取阶段过滤，不进入模型上下文 |
| 工具结果图片无法转为可见内容 | 思考卡片保留文字说明 | 明确标注“图片不可见”，不伪造多模态内容 |
| SSE 连接中断 | 已输出内容保留，显示重新生成 | 本轮工具消息不落库，重生成时历史仍干净 |

## 九、验收标准

| 编号 | 验收项 | 通过标准 |
|------|--------|---------|
| AC1 | 无关连续提问 | 同一会话先问“如何重置密码”并触发检索，再问一个无关问题；第二次回答不引用密码文档、不出现上一轮 Skill 步骤或旧链接 |
| AC2 | 历史清洁 | 刷新或翻页历史时，不出现 `<task_result>` 开头的假用户消息；思考过程仍可从 `steps` 还原 |
| AC3 | 模型上下文 | 通过调试日志确认：请求 `messages` 中不含 `<task_result>` 字符串；工具结果消息 `role=tool` 且 `tool_call_id` 与对应 `tool_calls[].id` 一致 |
| AC4 | 前端回归 | 前台与后台对话的正文流、推理流、思考卡片、重新生成、标题更新与停止生成均与改造前一致 |
| AC5 | 后台维护闭环 | `context_editor` 生成草稿后变更卡片正常显示；确认批次前模型回复仍提示“草稿未生效，请在对话内确认”；确认/回滚流程无退化 |
| AC6 | 多工具调用 | 一轮返回多个 `tool_calls` 时，每个调用都有对应 tool 结果；无重复调用、无流程中断 |
| AC7 | 越权防护 | 前台请求 `context_editor` 被拒；知识库文件无任何变化；思考卡片显示简短无权限提示，不含内部路径 |
| AC8 | 旧数据兼容 | 打开改造前含 `<task_result>` 的会话，该消息不展示、不进入新提问的模型上下文，新回答不受其影响 |
| AC9 | 上下文截断 | 超长会话触发 64000 字符权重截断时，被丢弃的是真实问答对；system 消息完整保留；无无头工具结果残留 |
| AC10 | 错误回注 | 工具加载失败/参数错误时，前端显示简短错误，服务端日志记录内部路径与堆栈，模型上下文不含内部路径 |
