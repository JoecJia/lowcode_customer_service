# 迭代抓手（把“智能客服”当成可持续演进的产品）

本文件用于把当前仓库的“智能客服”迭代方式产品化、工程化：稳定可控地升级 Skills、知识库与主控规则，并用低成本回归防退化。

## 1. 把 Skills 当作 API 来管

### 1.1 稳定面与演进面
- 必须稳定（不轻易变更）
  - Skill 的触发条件边界、输入输出结构、失败/兜底行为
  - `knowledge_retrieval` 的“索引定位 → 命中片段提取”的检索路径
  - `temporary_context_management` 的“record → process → 更新 index”的闭环流程
  - 主控的兜底逻辑与死循环监控要求
- 允许演进（可迭代优化）
  - Skill 内部的提示词表述、输出文案的精炼与更清晰的结构化表达
  - 反问策略的命中率与问题设计（在不改变输入输出约束的前提下）
  - 知识库内容覆盖度与索引关键词完善

### 1.2 Skill 规范模板（建议约束点）
每个 Skill 都应明确并尽量保持稳定：
- 触发条件：用户问什么/提供什么信息时触发；哪些情况必须先反问
- 输入：参数列表与约束（必填/可选/格式）
- 输出：固定结构（例如“操作路径 → 关键设置 → 注意事项”）
- 边界：不做什么；遇到信息不足如何处理；与哪些 Skill 协作
- 失败处理：失败判据、如何降级、如何记录到临时区

参考主控规范：[agent.md](../agent_config/agent.md)

## 2. 建立“知识闭环”流水线

### 2.1 闭环目标
- 把对话中的新增知识、模糊点、失败案例，先沉淀到临时区，避免“只在聊天里解决”
- 定期把高价值内容入库到 FAQ/产品文档/方案文档，并更新索引，让后续能被 `knowledge_retrieval` 命中

### 2.2 流程（record → process → 更新 index）
- 临时记录（每天）
  - 触发：答不准/答不全/需要人工/用户提供了新资料/出现新规则
  - 动作：调用临时记录机制，将内容写入当日 `temp_notes_YYYYMMDD.md`
  - 参考 Skill：[temporary_context_management.md](../agent_config/skills/temporary_context_management.md)
- 入库处理（每周）
  - 从临时区挑选 Top 问题与典型失败案例，归类到：
    - 常见问题：`agent_config/context/faq/`
    - 产品文档：`agent_config/context/product_docs/`
    - 业务逻辑/方案：`agent_config/context/logic/`
  - 同步补齐索引关键词与路径：`agent_config/context/index.md`

索引位置：[index.md](../agent_config/context/index.md)

## 3. 用小规模“回归集”防退化

### 3.1 回归集的目的
每次改动（Skill 规则、检索策略、话术结构）都用一组固定问题回放，关注：
- 意图分类是否变差（是否更容易走错 Skill）
- 回答是否更长更绕（信息密度是否下降）
- 是否出现新幻觉/越权建议（例如编造功能、路径）
- 追问轮数是否异常上升（反问策略是否过度）

### 3.2 回归集组织方式（不新增仓库结构的前提下）
建议先用“表格+断言点”的方式组织，后续再工程化为脚本化回放。

推荐把回归集内容维护在本文件中（或临时区汇总后再搬运到本文件），格式如下：

| CaseID | 用户问题 | 期望意图分类 | 期望调用 Skill | 必须命中的知识文件（可选） | 通过标准 |
|---|---|---|---|---|---|
| R-001 | 我导出 Excel 时手机号是脱敏的，怎么处理？ | 产品功能使用 | product_feature_usage + knowledge_retrieval | agent_config/context/product_docs/form_usage_guide.md | 给出"权限/脱敏设置"配置路径，含关键开关点 |
| R-002 | 填 A 表时如何自动带出 B 表手机号？ | 产品功能使用 | product_feature_usage + knowledge_retrieval | agent_config/context/product_docs/form_usage_guide.md | 明确"数据联动"四步：联动表/条件/字段/排序 |

### 3.3 回归集的初始规模
- Top 30 高频问题：覆盖导出、权限、数据联动、流程审批、数据工厂等高频主题
- Top 10 典型失败问题：覆盖“信息不足需要反问”“分类易混淆”“曾经出现幻觉的点”

## 4. 建议的迭代节奏（低成本但稳定）

### 每天
- 对无法准确解决的问题执行临时记录（闭环入口）
- 优先保证“可追溯”：记录用户问法、已给出的答复、缺失信息、下一步建议

### 每周
- 处理临时记录入库（FAQ/产品文档/业务方案）
- 回补索引关键词（确保能被检索到）
- 复盘“反问”是否必要、是否太多，并优化反问路径

### 每两周或每月
- 信息架构整理：合并重复知识、清理过期内容、补索引
- 回看回归集指标：解决率、平均追问轮数、需要记录的比例

## 5. 发布检查清单（更新—自测—提交—同步）

### 5.1 更新前
- 明确本次改动范围：改了哪个 Skill/哪类问题/是否涉及索引与知识库
- 如果改动涉及检索：确认 `agent_config/context/index.md` 有对应入口

### 5.2 自测（最小可用）
- 回放回归集中的相关 Case（至少覆盖本次改动涉及的 Top 问题）
- 检查回答是否遵循目标 Skill 的固定输出结构
- 若 `knowledge_retrieval` 命中片段包含图片引用，验证是否能把图片信息与文本一起输出

知识检索规范：[knowledge_retrieval.md](../agent_config/skills/knowledge_retrieval/knowledge_retrieval.md)

### 5.3 提交前
- 工作区干净：`git status` 无未提交文件（除预期修改外）
- 不引入大文件：确认 `documents_all/` 等目录不会进入提交
- 路径一致性：文档/索引中不得出现本机绝对路径（file 协议链接、Windows 盘符路径、用户家目录路径等），统一使用相对仓库根目录的相对路径；修改知识库内容后需同步重建向量索引

### 5.4 提交信息规范（建议）
- `feat:`：新增能力（例如“知识检索返回命中图片信息”）
- `fix:`：修复问题（例如“修复索引路径错误”）
- `docs:`：仅文档与知识库内容调整
- 提交信息包含“改了哪个 Skill/哪类问题”，便于回溯

### 5.5 同步（统一流程）
- 直接使用原生 git 命令同步，不依赖同步脚本：
  - 拉取：`git pull --rebase --autostash origin main`（自动暂存未提交改动再 rebase）
  - 推送：先执行上述拉取，再 `git push origin main`
  - 提交：按文件精确 `git add <文件>`，严禁 `git add -A` 提交无关/敏感文件

## 7. 智能体拆分方案（方案 A：双智能体）

> **状态**：方案已确认（待开发）
> **对应清单**：T-007
> **最后更新**：2026-11-10

### 7.1 目标与分工

将单一客服智能体拆分为「前台客服智能体」与「后台维护智能体」，二者复用同一套运行引擎（`agent_loop_stream` 多轮循环 + SSE + 会话存储 + 检索链路），仅在**系统提示词**、**技能白名单**、**入口与鉴权**上区分。

| 智能体 | 入口 | 鉴权 | 技能（Skill） |
|--------|------|------|---------------|
| 前台客服 | `POST /api/chat`（已有） | `get_current_user`（`can_chat`） | `product_feature_usage`、`usage_scenarios`、`scenario_solutions`、`build_business_system`、`knowledge_retrieval`、`clarifying_questions`、`feedback_form_link`（含 `_encode`） |
| 后台维护 | `POST /api/admin/chat`（新增） | `require_admin`（`can_admin=1`） | `context_transformation`、`temporary_context_management`、`knowledge_retrieval`（只读，用于改文档前定位内容） |

### 7.2 方案 A 总览（不物理拆目录）

不搬迁 `agent_config/` 目录结构，仅做「提示词 + 技能白名单」分流：

- 新增 `agent_config/agent_admin.md`（后台智能体系统提示词）；现有 `agent_config/agent.md` 作为前台智能体。
- `SKILL_REGISTRY` 保留全量，新增 `AGENT_PROFILES = {"frontend": [...], "admin": [...]}` 做技能白名单。
- `get_system_messages(profile)` 按 profile 选提示词文件，并只渲染该 profile 的 `TOOL_PROTOCOL` + MCP 工具目录。

**为什么选方案 A**：技能脚本相对路径、`context/assets` 静态挂载、检索索引扫描均无需改动，改动面小、易回滚。

> 备选方案 B（物理拆 `agent_config/frontend/` 与 `agent_config/admin/`）需同步改前端资源路径、`search_service` 索引扫描、`main.py` 静态 mount、`SKILL_REGISTRY` 路径，成本高，暂不采用。

### 7.3 后台智能体的 Context 写能力（核心问题）

**结论**：仅靠「某个接口」无法让智能体直接改文件。模型本身没有文件 / 网络 / Shell 权限，必须由后端把「改文件」包装成它能调用的工具（`<task>` 技能 或 MCP 工具）。当前项目不存在任何此类工具（`context_transformation` 技能仅描述「请执行 python 脚本」，运行时并无执行命令能力，属既有缺口）。

| 方案 | 做法 | 优点 | 缺点 | 建议 |
|------|------|------|------|:--:|
| 1. 内置受控工具集 | 在 `dispatch_skill` 中新增分支，暴露受控原语：`context_list` / `context_read` / `context_write` / `context_append` / `context_delete`、`context_transform_document`、`context_update_index`、`context_compress_assets`、`temporary_context_record/view/process` | 与现有 `<task>` 机制无缝、可控、可审计 | 需新增后端代码 | ✅ 主推 |
| 2. 本地 MCP Server | 起一个「context-admin」MCP Server，把文件操作暴露为 MCP 工具，仅后台智能体挂载 | 协议化、可复用 | 需额外进程 / 依赖 | 可选演进 |
| 3. 沙箱命令执行 | 给后台智能体一个白名单 shell 工具（仅允许 context 目录内、仅允许白名单脚本） | 灵活 | 权限面最大、风险高 | ❌ 不推荐 |

**推荐**：方案 1 为主，后续如需统一工具协议再演进到方案 2。

**写入采用「两阶段确认」**（已拍板）：

1. **生成阶段**：智能体的写操作只落到暂存区 `agent_config/context/.staging/<change_id>/`，不直接改 `context/`；同时返回变更摘要（目标文件、新增 / 替换内容、diff 预览）。
2. **确认阶段**：前端在对话框中展示变更卡片（文件路径 + diff + 「确认并入」/「取消」）。
3. **应用阶段**：确认后调用 `POST /api/admin/context/changes/{change_id}/apply`，后端才把暂存文件合并进 `context/`，并触发 `update_index.py` 增量索引、写入 `context_audit_log`。
4. **取消 / 超时**：`discard` 接口主动清理，或 TTL（建议 24h）自动回收。

> 暂存区 `.staging/` 需加入 `.gitignore`，且不参与检索索引扫描。

### 7.4 会话与上下文隔离

「同一套 context」分两层理解：

- **知识库** `agent_config/context/`：两智能体共用同一份文件（前台只读检索，后台读写维护）。
- **对话上下文**（`sessions` / `messages`）：按 `scope` 隔离，避免前台用户会话与后台维护会话混池。

改造：`sessions` 表新增 `scope TEXT DEFAULT 'frontend'`（取值 `frontend` / `admin`），列表与创建接口按 scope 过滤。

#### 7.6.2 交互逻辑

```
点击右下角 icon
    → 展开悬浮对话框，恢复上次激活的 Tab（无 Tab 则自动新建）

点击「历史记录」
    → GET /api/admin/sessions（scope=admin）
    → 弹窗展示历史会话列表（标题 / 时间 / 消息数）
    → 点击某条记录
        ├─ 该会话已在 Tab 中 → 直接激活
        └─ 未在 Tab 中 → GET /api/admin/sessions/{id}/messages → 新建 Tab 并加载

点击「新建对话」
    → POST /api/admin/sessions → 新 Tab，标题 =「新对话」，消息区为空

首轮问答结束
    → POST /api/admin/sessions/{id}/auto-title
    → 生成前 Tab 标题保持「新对话」；生成后回显 ≤20 字标题（对应 T-010）

重命名
    → 弹窗内手动改名（PATCH /api/admin/sessions/{id}）
    → 或点击「AI 重新生成」再次调用 auto-title

点击「收起」
    → 仅隐藏对话框，Tab 与 SSE 连接不销毁，生成继续（为 T-012 静默生成打底）

多 Tab 并发流式
    → SSE 由 useMaintenanceChat 持有，切换 Tab 不中断
    → 生成中的 Tab 显示 loading 点，完成后自动写入消息
```

### 7.7 安全与审计

- 后台对话接口强制 `require_admin`。
- context 写操作路径规范化校验：`os.path.realpath` 后必须位于 `agent_config/context/` 之内，拒绝目录穿越。
- **写操作两阶段隔离**：暂存区 `.staging/` 与正式 `context/` 物理分离，未确认不落盘。
- 写操作前自动备份（`.bak` 或 git 快照），失败可回滚。
- 新增审计表 `context_audit_log`（操作者 / 时间 / 动作 / 目标文件 / 摘要）。
- 仅允许 `.md` 等文档类型写入；脚本执行限定白名单（`transform_document.py`、`update_index.py`、`compress_assets.py`）。

### 7.9 风险与回滚

| 风险 | 应对 |
|------|------|
| 提示词 / 技能白名单误配导致前台能力缺失 | profile 白名单集中配置，单测覆盖技能渲染 |
| 后台智能体越权写文件 | 路径 realpath 校验 + 白名单 + 审计表 |
| 写操作破坏知识库 | 两阶段确认（暂存区）+ 写前备份 + git 快照，支持回滚 |
| 会话混池 | `scope` 隔离 + 列表过滤 |
| 多 Tab 并发流式状态错乱 | 每 Tab 独立 `sessionId` 与流式缓冲，SSE 由 composable 统一持有 |
| 暂存区残留 / 无人确认 | TTL 自动清理 + 审计表可追溯 |
| 自动命名失败 | 降级为取首句前 20 字作为标题 |
